# 디지털트윈 유형별 표현 · 구현 계획 초안 (2026-09-15)

> 상태: 초안. 정본이 아니다. 03 제2부(§20~§29)의 화면 사양을 코드로 옮기는 작업 순서와 데이터 조달 방식을 정리한다.
> 답이 나오면 README §7 I 묶음에 맞물려 정본에 올리고 이 파일은 `docs/레거시/작업/`으로 내린다.
>
> 기준: 화면은 03 제2부가 정했다. 여기서는 **무엇을 실데이터로 굽고 무엇을 시나리오로 두는가**, **어떤 부품을 어떤 순서로 만드는가**만 정한다.
>
> 진행 (2026-09-15 저녁): 사용자 지시 "실데이터 없이 디자인으로 구현"에 따라 **T2 표현 부품 일곱과 T3 유형별 장면 일곱을 시나리오 데이터로 전부 만들었다**(03 §27).
> T1 실데이터 굽기는 시작하지 않았다(키 발급 전). T4 검수는 헤드리스 캡처로 유형마다 한 번씩 봤고 `검수/`에는 아직 안 붙였다. 전망 탭(scr-02) 연결은 남았다.

## 1. 지금 기준선

- 데모는 서버 없는 정적 앱(Netlify)이다. 외부 데이터는 `scripts/fetch-*.mjs`가 한 번 받아 `public/weather/*.json`으로 굽고 앱이 읽는다.
  바람·강수·기온·상층장(Open-Meteo ERA5), 해수온이 이 방식이다. 라이브 호출은 생활안전지도 WMS 타일뿐이다.
- 시나리오 날짜는 2024-09-21이다(02 §5.4). 굽는 실데이터도 이 날 또는 자료가 있는 가장 가까운 날로 맞춘다.
- 화면 부품: 면 층(범위·영향 폴리곤), 핀(장비·시설·대피소), 시간축, 기준·대안 비교 카드, 근거 카드, 조건 카드(유형·지역·조건), 훈련 기록, 열돔 지구본.
- 데이터 계약: `model/forecast.ts`(예측판·눈금·지표), `model/training.ts`(조건 세트·지역·스냅샷), `adapters/`(실데이터 → 이벤트 봉투).

## 2. 원칙

1. **실데이터는 굽는다.** 키는 스크립트 실행 환경에만 있고 앱에는 JSON만 간다. 실시간처럼 보이게 하지 않는다.
2. **굽는 범위는 "현재 조건의 근거"까지다**(03 §20). 미래 장면(침수면·범람면·화선·변위·장애 전파)은 fixture 시나리오다.
3. **화면 생성 층**(풍향 화살표, 연기 플룸, 상태 변화, 경로)은 앱이 실데이터와 시나리오를 엮어 그린다. 계산이 아니라 표현이다.
4. 못 가져오는 항목은 fixture에 시나리오로 두고 머리에 출처와 이유를 적는다. 화면에는 관측시각·출처만 쓴다(03 §20).
5. 한 부품은 한 번 만들어 전망 탭과 디지털트윈 메뉴가 같이 쓴다.

## 3. 데이터 조달 결정

| 유형 | 굽는 실데이터 | 출처 · 키 · 형식 | 시나리오(fixture) | 화면 생성 |
|---|---|---|---|---|
| A 도시침수 | 강우 격자·예보 (있음), 레이더 강수영역, AWS 강우 | Open-Meteo(키 없음) · 기상청 API허브(키) | 침수면·침수심 4~5장, 펌프 대안, 도로 통제 | 침수 진하기, 도로 상태 |
| B 하천범람 | 관측소 수위·유량·우량, 홍수특보 | K-water OpenAPI(공공데이터포털 키, 10분/30분/시간) · 홍수통제소 | 미래 수위, 범람면, 고립 구역, 대피 상태 | 종단도(실측 구간 + 시나리오 구간) |
| C 해안월류 | 파고·파주기·파향·풍향, 조위 | 기상청 해양기상 부이(API허브 키) · 해양조사원 현행 국가중점데이터(명세 확인 뒤, 안 되면 시나리오) | 월류 지점·시각, 침수면, 차수 대안 | 방호시설 선, 월류 지점 강조 |
| D 산불 | 위성 활성화재 관측점, 풍향·풍속, (선택) 광역 연기 | NASA FIRMS(MAP_KEY 무료, CSV) · Open-Meteo · CAMS | 발화점, 화선 4장, 방화선, 대피경로, 시설 도달시각 | 풍향 화살표, 연기 플룸(풍향 × 시간) |
| E 폭염 | 기온·습도, 폭염특보, 무더위쉼터, 인구 격자 | Open-Meteo · API허브 · 공공데이터포털(쉼터) · 통계지리(정적) | 취약대상 집계, 누적 노출, 쉼터 연장 효과 | 격자 색·해칭·공백 외곽선 |
| F 급경사지 | 누적 강우, 산사태 예측정보, 위험지도 | Open-Meteo · 산림청(키·WMS 여부 확인) | 변위 mm·벡터, 시설 상태, 통제 구역 | 벡터 화살표, 상태 색 |
| G 정전 파급 | 전력수급 현황(광역 맥락만) | 전력거래소 | 계통도, 노드 상태, 중단 권역, 복구 순서 전부 | 노드 꺼짐·켜짐, 연결선 점선 |

키가 필요한 곳은 셋이다. 공공데이터포털, 기상청 API허브, NASA FIRMS. 셋 다 무료 발급이다. 못 받는 항목은 그 항목만 시나리오로 내린다.
조위(해양조사원)와 산사태 위험지도(WMS)는 현행 명세 확인이 먼저다(README §10).

## 4. 작업 묶음

### T1. 데이터 굽기와 어댑터

- `scripts/fetch-<type>-*.mjs`를 유형별로 1~2개. 기존 `fetch-wind-field.mjs` 패턴(날짜·범위·출력 경로·근거 주석).
- 산출: `public/data/<type>/*.json`. 어댑터 `adapters/<source>.ts`가 이벤트 봉투(E0·E1·E3·E4 등)로 옮긴다. 원본시각은 보존하고 시나리오 시계에 매핑한다(02 §5.5).
- 실패 시 앱은 fixture로 물러난다. 굽기 실패가 화면을 깨지 않는다.

### T2. 표현 부품 (03 §24 순서)

| 부품 | 만드는 것 | 재료 |
|---|---|---|
| 광역 인셋 | 우하단 작은 지도 + 지역 위치 표시 + 시간 동기 + 클릭 시 메인과 전환 | 기존 바람·강수·기온 층 재사용, 열돔 지구본은 `globeHeight`로 축소 |
| 조건 요약 카드 | 좌하단 날씨 카드를 유형별 조건 요약으로. A~F 날씨, G 장애 원인·전력 상태 | `TwinWeather` 확장 |
| 선 층 | 방호시설·방화선·대피경로·통제 경계. `lib/map-polygon.ts` 옆에 `map-line.ts` | MapLibre line 레이어, geometry 표 확장 |
| 노드·연결 | 시설 노드 핀(상태 색) + 의존 연결선(실선/점선) | symbol + line 레이어, fixture 계통 정의 |

| 격자 면 | 생활권·격자 색 + 해칭 + 외곽선 | fill 레이어 3장(색·패턴·외곽) |
| 보조 분석뷰 | 화면 아래 패널. 종단도(SVG 선 그래프 + 기준수위선), 계통도(SVG 노드·연결) | DS 차트 없음 → `src/components/`에 `// TODO(ds)` 표식 |

### T3. 유형별 장면 채우기

부품이 생기는 순서대로. A → C → D → B → F → G → E. 시연 우선순위에 따라 D를 앞으로 당길 수 있다.

| 유형 | 더할 것 |
|---|---|
| A | 인셋(강우 레이더·조위 곡선), 조건 요약, 건물 저층부 강조(선택) |
| C | 방호시설 선, 월류 지점 강조, 인셋(조위·풍향·파고), 내수침수 연결 표시 |
| D | 위성 관측점(●)·발화점(🔥) 구분, 풍향 화살표, 플룸, 방화선·대피경로 선, 시설 상태 4단계, 인셋(풍향장) |
| B | 종단도 보조뷰, 관측소 순서·구간 도달시간, 고립 구역, 인셋(유역) |
| F | 변위 벡터, 시설 상태 색, 통제 경계, 위험지도 배경, 인셋(누적 강우) |
| G | 계통도 보조뷰, 노드 핀·연결선, 복구 순번 |
| E | 격자 장면 신설(색·해칭·공백), 쉼터 핀, 조건·대안 세트, 열돔은 인셋으로 |

### T4. 검수

- 유형마다 03 §26 다섯 항목으로 한 번씩. 헤드리스 캡처를 `검수/`에 붙인다.
- 03 §27 구현 상태 표를 유형이 끝날 때마다 갱신한다.

## 5. 정해야 할 것

1. 키 발급: 공공데이터포털, 기상청 API허브, NASA FIRMS. 못 받는 쪽은 시나리오로.
2. 시나리오 날짜 2024-09-21 고정 유지 여부. 유지하면 그날의 실제 강우·수위를 굽는다.
3. T3 순서. 시연에서 먼저 보일 유형.
4. 앞서 남은 셋: B 메뉴 유지, G 자리(A 파생이면 계통도 보조뷰가 A에도 붙는다), E 격자 장면 제작(이 계획대로면 만드는 쪽).
5. 조위·산사태 위험지도 현행 명세 확인 담당.

## 6. README §7 I 묶음과의 관계

- T1·T2는 I0 기반(계약·어댑터)과 I4 선택 확장(표현 부품)에 걸친다. 대표 데모 D0~D8 주동선을 막지 않도록 A·C부터 붙인다.
- T3의 B·D·E·F·G는 I4다. 일정에 따라 유형 단위로 끊는다.
