방향과 검토 질문

근거 · README §2 근거 · README §5 근거 · README §6
원본 자료와 추가 조사 결과를 기준으로 CUVIA의 제품 방향을 새로 설계하고, 여러 이벤트를 하나의 재난 사건으로 해석해 디지털트윈 예측과 대응에 활용하는 방식을 대표 데모로 증명한다. 재난이 발생하기 전에 미래 영향을 예측하고, 대응을 바꿨을 때 달라지는 결과까지 비교한다. 이 조건에서 우리 규정이 통하는지 확인하고, 안 통하는 지점을 고칠 거리로 남긴다.

Phase 2가 답해야 할 다섯 질문

  1. CUVIA는 어떤 원천 데이터와 이벤트를 수집하는가?
  2. 서로 다른 이벤트를 어떤 기준으로 하나의 재난 사건에 연결하는가?
  3. 사건 유형에 따라 디지털트윈의 입력, 시간축, 공간 표현과 결과가 어떻게 달라지는가?
  4. 예측 결과가 담당자의 판단, SOP, 전파, 조치와 기록으로 어떻게 이어지는가?
  5. 이 방향을 한 건의 대표 사건으로 어떻게 이해하기 쉽게 시연할 것인가?
  6. 모의훈련 자체. 자사 경쟁 비교표에서 CUVIA ◎, 경쟁 5사 X다(요약설명자료 슬3). 타사 7건에 훈련 기능이 없다.
  7. 실제 사건이 훈련 시나리오가 된다. 제안서 p.16 "과거재난이력으로 가상재난 발생 시나리오를 자동 생성"을 사건 원장이 받친다.
  8. 단일 재난 시나리오를 조합한 복합 재난 시나리오(제안서 p.15).
  9. 트윈 위에서 시나리오가 전개된다. 수치는 기준 ③을 넘는 것만 선다(24년 도시침수 완료보고 p.39·40 조건별 시나리오 DB가 대표 경로).
  10. 결과가 개선 항목으로 이어진다. 타사 7건에는 이 고리가 없다.
  11. 대응은 SOP에서만 나온다. SOP는 센서 임계에서 발동한다. 대응 목록을 사건마다 손으로 적지 않는다.
  12. 훈련 지표는 하나다. 발동에서 조치까지 걸린 시간. 창원천이면 14:35 예측 → 15:22 통제 = 47분.
  13. 대안 시각은 셋 중 하나다. 알린 직후(이론상 최선 · 준비 시간은 확인 전까지 0으로 두고 상한이라고 적는다) ·
  14. 결과는 경로가 있는 것만 세운다. 없으면 시간(도달 전 여유 · 지속 시간)만, 그것도 없으면 상황 부여(수치 없음).
  15. 조건 단계는 규정이 버티는 한계를 드러내는 문턱에만 둔다. 세기 눈금을 늘리지 않는다.
  16. 결과 경로가 없는 항목은 훈련에 넣지 않는다. 주민 전파가 그 예다 — 대피율·부상은 우리 데이터에 없고,
설계 원칙 (README §5)
  • 사건 중심: 센서나 기능 목록보다 담당자가 판단하고 대응할 사건이 중심이다.
  • 원천과 판단 분리: 수집값, 관측 이벤트, 시스템 판단, 담당자 확인을 구분한다.
  • 현재와 미래 분리: 현재 관측, 조건 유지 전망, 대안 전망과 실제 결과를 구분한다.
  • 공통 골격과 유형별 차이: 업무 흐름은 공통으로 두고 트윈의 입력·표현·결과는 유형별로 설계한다.
  • 사람 승인: AI와 예측은 근거와 권고를 제공하며 되돌리기 어려운 조치는 담당자가 확정한다.
  • 근거 추적: 화면의 판단과 예측 결과는 사용한 데이터, 시각, 출처와 가정으로 돌아갈 수 있어야 한다.
  • 데모 데이터는 내부에서 구분: 실제 API·원본·승인 표본·시나리오 데이터·사용자 입력과 계산 주체는 데이터 계약·fixture·adapter·기획 문서에서 구분해 실제 연계로 교체할 수 있게 한다. 기본 UI에는 이 제작 구분을 상태 칩이나 면책 문구로 노출하지 않는다. 관측시각·갱신시각·출처기관·모델 버전처럼 실제 제품 판단에 필요한 정보만 해당 화면의 근거로 표시한다.
  • 혼합 데모: 확보 가능한 실제 API·원본 재생·승인 표본은 쓰고, 확보하지 못한 내부 연계는 시나리오 데이터로 채운다. 하나의 사건 기준시각을 유지하고 이벤트별 원본시각·시나리오시각·교체 대상은 내부 데이터 계약과 02 §5.4에 기록한다. 화면은 하나의 제품 경험으로 연결하되 검증하지 않은 정확도·운영 실적을 실제 성과로 대외 주장하지 않는다.
  • 대표 데모 집중: 모든 유형의 전체 흐름을 구현하지 않고 한 사건으로 깊이를 증명한다.
  • 시연 우선 연결: 데모는 제품 방향을 확인하는 시연이다. 화면 완성도가 아니라 기획 문서와 끊김 없이 연결되는지를 기준으로 삼고, 합성 데이터는 같은 이벤트 계약과 사건 기준시각을 따른다.
  • 수량 비목표: 화면, 사건, 재난유형 수를 Phase 2의 성과로 삼지 않는다.

먼저 가르는 세 축

기존 문서와 화면에서 이벤트 유형, 재난유형, 처리상태가 섞이면 같은 단어가 서로 다른 질문에 답하게 된다. Phase 2에서는 아래 네 축을 독립적으로 관리한다.

하나의 수위 관측 이벤트는 내수침수·하천범람·폭풍해일 사건에 각각 근거가 될 수 있다. 반대로 하나의 내수침수 사건에는 강우, 관로수위, 도로수위, 펌프 상태, 조위, CCTV와 현장 보고가 함께 연결될 수 있다. 태풍·집중호우는 기본적으로 사건의 기상 조건이며, 독립 담당·조치·처리상태가 필요한 경우에만 사건 위험유형으로 등록한다. 사건 위험유형과 A~G 트윈 유형군의 기관별 매핑은 대상 기관 분류를 확인한 뒤 정한다.

외부 기관 사건은 externalRecords[]에 원본 ID·상태·변경 이력을 우선 보존한다. 외부 기록 수신만으로 CUVIA Incident를 자동 생성하거나 병합하지 않는다. 시간·공간·위험현상이 맞으면 관계 후보를 제안하고, 담당자 확인 뒤에만 내부 Incident를 만들거나 외부참조 관계를 확정한다.

시설 상태변경은 항상 evidenceEvents[]에 악화·완화 조건으로 연결한다. 시설 장애가 별도 담당 조직, 독립된 조치와 처리상태를 가져야 할 때만 기반시설 장애 Incident를 만들고 원인 사건과 악화 또는 파생 관계로 연결한다.

특보 발표·변경은 공식 상황 이벤트와 알림을 만들고 감시 우선순위를 높일 수 있다. 센서의 관측 위험단계는 해당 센서 규칙으로만 바뀐다. 센서·API·VLM·Forecast를 결합한 위험도 매트릭스 결과와 사전 정의된 단일·복합 조건으로 알림과 사건 후보는 자동 생성할 수 있지만, 그 결과만으로 도시 대응단계를 자동 격상하지 않는다.

도시 대응단계는 개별 Incident의 workflowStatus가 아니라 별도 CityOperationalState로 관리한다. 변경 시 CITY_STAGE_CHANGED 업무 이벤트를 남기고, 변경을 승인한 Decision과 해당 시점의 관련 사건을 references[]와 relatedIncidentIds[]로 연결한다. Incident에는 판단 당시 도시 대응단계의 참조만 보존한다.

  • pendingDecisionId는 decisions[] 중 검토중 상태인 결정안을 가리킨다.
  • 결정 상태는 검토중·선택·승인·기각·취소로 통일한다. 결정안 생성은 검토중, 담당자의 안 선택은 선택, 최종 권한자의 확정은 승인으로 기록하며 추가 확인은 검토 요청을 유지하는 결정 사유다.
  • Action의 처리상태는 대기·진행중·성공·실패·미응답·확인대기·대체됨·취소로 통일한다.
  • FIELD_REPORT_RECORDED는 현장 담당자가 보낸 원천 보고, ACTION_STATUS_CHANGED는 배정된 Action의 상태 변화, OUTCOME_RECORDED는 관측·보고·조치 결과를 종합한 사건 단위 검증이다.
  • 대체 Action은 replacesActionId로 실패·미응답 Action을 참조하며 기존 Action 기록을 덮어쓰지 않는다.
  • ACTION_*은 현장 확인·도로 통제·시설 점검과 운영 요청처럼 사람이 수행하는 업무에 사용한다.
  • CONTROL_*은 장비에 실제 원격제어 명령을 보내는 경우에만 사용하며 Phase 2 대표 데모에서는 쓰지 않는다.
  • DISSEMINATION_*은 알림톡·방송·전광판·기관 통보 등 메시지 전파 요청과 채널별 결과에 사용한다. 전파문 본문은 §2.4의 CAP 1.2 필드(식별자, 심각도·긴급도·확실성, 대상지역, 갱신·취소) 구조를 따른다.

모델·예측 상태는 실행 여부와 결과 가용성을 섞지 않는다. 제품 범위 밖이거나 요청하지 않은 경우는 미지원·미실행, 필요한 입력·기능이 없어 대안을 만들 수 없으면 Forecast 가용상태를 대안 계산 불가, 실제로 시작한 실행이 오류로 끝난 경우만 ModelRun을 실패로 기록한다. 권고와 결정의 대응수준 값은 실제 기관 SOP 확인 전 감시 강화·현장 확인·선제 통제 검토·통제·종료 검토 같은 데모 역할명으로 두고, 공식 대응단계처럼 표현하지 않는다.

Incident의 공간 범위는 한 현장으로 고정하지 않는다. 같은 원인·영향·담당·대응으로 관리할 업무 단위가 기준이며 지점, 시설, 구역, 회랑, 지구, 도시 전역을 모두 수용한다. 광역 재난도 하나의 Incident가 될 수 있고, 그 안에서 독립된 담당·조치·처리상태가 필요한 지역·시설 상황은 연관 Incident로 분리한다.

같은 공간에 있다는 이유만으로 이벤트를 사건 근거에 포함하지 않는다. 시간·원인·영향·업무 관계를 확인해 선택한 알림 또는 사건에 연결하며, 같은 지구의 미연결 이벤트는 지구 전체 현황에서 구분해 보여준다.

THRESHOLD_CROSSED와 RATE_CHANGED는 원천 이벤트가 아니라 관측을 규칙으로 변환한 파생 이벤트다. 위험평가와 권고는 모델·규칙의 해석이 포함된 분석 이벤트다. 사건 상태·관계, 결정과 실행 이벤트는 원천 관측이 아니라 CUVIA 안에서 발생한 업무 기록이다. 어떤 원천·규칙·담당자 행위에서 만들어졌는지 추적해야 한다.

모든 이벤트를 사용자 알림으로 띄우지 않는다. OBSERVATION_RECORDED 같은 원천 이벤트는 우선 기록하고, 다음 규칙 중 하나가 충족될 때 AttentionAlert를 생성·갱신한다.

알림 유형입력과 조건알림 결과사건 후보와의 관계
단일 심각 알림핵심 센서의 심각 임계치, 명시적 VLM·현장 위험, 외부 기관 사건처럼 즉시 검토가 필요한 단일 근거담당자 확인 알림사건 후보를 바로 생성할 수 있음
복합 징후 알림같은 공간·시간창에서 센서 임계치·변화율, 특보·기상 조건, VLM, 시설 상태가 정한 조합을 충족근거 묶음과 연결 이유를 표시사건 후보 생성 또는 기존 후보 우선순위 갱신
예측 영향 알림디지털트윈·외부 모델 Forecast가 예상 침수심·도달시간·영향 대상 등 사전 정의 기준을 초과예상 시각·영향 공간·모델 근거를 표시후보 생성, 기존 사건의 위험판단·대응 검토 갱신
품질·연계 알림결측·지연·모델 실패·시설 미응답이 현재 판단이나 대응에 영향을 줌누락 근거와 대체 확인 경로를 표시사건을 자동 확정하지 않고 검토 요청 또는 기존 사건 갱신

AttentionAlert는 alertId, 제목(무슨 일이 일어났나), 알림 유형·등급, 상태, 생성·갱신시각, 대상 공간·업무, evidenceEventIds[], forecastIds[], 연결 이유, 규칙 ID·버전, 담당·확인시각, 반복 억제·해제 정보를 가진다. 같은 원인의 반복 이벤트는 알림의 근거와 갱신 이력으로 누적하고 화면 알림 수를 무한히 늘리지 않는다. 원천 이벤트는 그대로 보존한다.

알림 규칙은 다음 순서로 평가한다.

  1. 데이터 품질과 유효시간을 확인한다.
  2. 지점·시설·배수권역 등 공간 연결 키를 적용한다.
  3. 임계치·변화율·VLM·특보·시설·Forecast 조건을 단일 또는 복합 규칙으로 평가한다.
  4. 같은 원인의 기존 알림과 사건을 찾아 생성·갱신·억제 중 하나를 결정한다.
  5. 사건 후보 기준을 충족하면 근거와 연결 이유를 가진 Incident(후보)를 생성하거나 갱신한다.

정확한 수치, 지속시간, 변화율 시간창, 공간 거리, 반복 억제시간과 등급은 I0 복합 알림 규칙표에서 관리한다. 현재 운영 원본이 없는 값은 데모 시나리오 조건으로 두고 실제 운영 기준처럼 사용하지 않는다.

제품 자료의 복합 위험도 분석(다지표 가중)을 기준으로 수위·강우·영상 맥락을 중심에 두고 시설 상태, 디지털트윈 Forecast와 데이터 품질을 함께 평가한다. 일반적인 발생가능성×영향도 표로 임의 치환하지 않는다.

사건 후보가 만들어지는 조건 (01 §7.1)

사전 감시는 아직 Incident가 아니다. 예측강우·특보·취약성만으로는 감시 우선구역·카메라·시설을 선정하고, 위험이 해소되면 별도 사건 상태 전환 없이 감시 우선순위에서 내린다.

다음 중 하나가 발생하면 Incident를 후보 상태로 만들 수 있다.

  • 외부 기관 사건이 새로 접수되거나, 공식 특보에 대해 별도 담당·조치·처리상태가 필요한 대응 업무가 시작됨
  • 핵심 센서가 심각 임계치를 통과함
  • 여러 센서의 변화가 동일 구역과 시간창에서 함께 나타남
  • VLM 또는 현장 보고가 명시적인 위험 장면을 확인함
  • 예측 결과가 사전에 정한 사건 후보 영향 기준을 초과함
  • 담당자가 수동으로 사건을 등록함

예측판이 갱신됐다는 사실 자체로는 후보를 만들지 않는다. 사전에 정한 영향 기준을 넘은 예측 결과만 위 조건에 따라 후보 근거가 된다. 대표 데모에서는 예측강우 상향으로 D0 감시 우선대상을 정하고, 관로수위 급상승과 침수예측판(E8)이 함께 나타나는 D1에서 사건 후보를 만든다. 후보 생성은 사건 확정이 아니다.

P0는 대표 사건과 시연 방식 자체를 결정하는 필수 확인 항목이다. P1은 시연의 구체성과 신뢰도를 높이는 항목이며, P2는 검증 메시지를 강화하는 항목이다. 확인되지 않은 값을 실제 사실처럼 임의 보완하지 않으며, 시나리오 데이터가 필요하면 오른쪽 열의 구성 원칙을 적용하고 원본 정보와 실개발 교체 대상을 내부 계약에 기록한다.

현재 원본 검토 결과 P0 네 항목은 모두 부분 확인이다. 다음 검토에서는 자료가 있다는 설명이 아니라 실제 파일·API 명세·식별자·기준시각을 받아 각 항목을 확인 또는 미확보로 닫아야 한다.

P0 확인 결과에 따라 사건의 현상·예측 데이터는 다음 세 방식 중 하나를 선택한다.

  1. 정렬된 과거 재생: 같은 과거 사건·기준시각에 속하는 E0~E8만 함께 재생한다. 시설·영상·대안 예측판이 그 묶음에 없으면 모의로 보충하지 않고 해당 기능을 비활성화한다.
  2. 혼합 데모: 실제 API·원본 파일·승인 표본·합성 데이터를 하나의 사건 기준시각에 맞춰 조합한다. 이벤트마다 dataOrigin과 ingestionMode를 내부 계약에 기록하고, 다른 지역·시점의 자료를 사건에 맞게 바꾼 경우 원본 재생이 아닌 합성 데이터로 분류한다.
  3. 완전 모의: 정렬된 과거 묶음이 없으면 E0~E8 전체를 하나의 시나리오 사건 세트로 만든다. 화면은 동일한 제품 UI를 사용하고 데이터 성격과 교체 대상은 내부 계약에서 관리한다.

담당자의 결정·현장 입력은 세 방식 모두 시연 방식 수동, 시연 중 CUVIA가 실제 생성한 업무 이벤트는 실시간으로 남기며 연계 준비도는 모두 내부 생성이다. 이는 현상·예측 데이터 혼합이 아니다. 과거 자료와 합성 데이터를 조합할 때도 사건 기준시각·원본 정보·변환 규칙을 내부에서 유지한다.

정렬된 원본·재생 자료와 실제 모델 결과로 전체 흐름을 구성할 수 있을 때 A 유형을 R2 시연으로 올린다. 혼합 데모나 완전 모의만 가능한 동안에는 R1 설계를 유지한다. 제품 화면에는 제작 면책을 노출하지 않으며, 시나리오 데이터와 실제 연계의 구분은 내부 계약·기획 문서와 필요한 경우의 대외 설명에서 관리한다.

모든 축소안을 적용해도 이벤트를 사건으로 묶는 이유, 근거와 한계, 담당자 승인, 실행·결과 기록은 데모로 증명할 수 있다. 다만 실제 기준·대안 결과가 없으면 디지털트윈의 비교 효과는 제품 방향 가설로만 보여주며 보유 모델의 성능이나 실제 대응 효과로 설명하지 않는다.

확인 결과에 따라 세부 값과 화면 표현은 바꿀 수 있지만, 수집→사건화→교차확인→기준 전망→ 영향 기반 대응→결과 기록이라는 골격은 유지한다. 대안 예측과 실제 대비 성능 검증은 해당 데이터를 확보했을 때 이 골격에 추가한다.

확정된 현재 역할은 예측 오차 확인과 사후 개선 항목 도출까지다. 유사 사건 추천, SOP 임계값 개선, 모델 보정·재학습으로 잇는 것은 향후 활용이며 Phase 2 확정 기능이 아니다. 모델 축 개선 항목은 검증 출처에서만 나온다. 모의훈련 결과로 모델을 고치지 않는다(자기 출력 순환).

7. IA-02 사건 작업공간

역할

사건 후보가 왜 만들어졌는지 확인하고, 담당자가 실제 사건 여부와 관계를 결정하는 중심 화면이다. 사건 작업공간은 특정 현장 하나를 뜻하지 않는다. 사건의 scope에 따라 지점·시설·구역·지구·도시 전역을 같은 구조로 다루며 지도 범위와 정보 밀도가 함께 바뀐다.

영역역할

좌측 관련 이벤트 현황선택한 복합 알림 또는 사건과 연결된 관측·특보·VLM·시설·Forecast·품질 이벤트를 시간순으로 표시

사건 생성 전에는 선택한 복합 알림을 구성한 이벤트를, 사건 생성 후에는 해당 Incident에 연결된 이벤트· 판단·예측·조치를 보여준다. 같은 지구에서 발생했어도 현재 사건과 연결되지 않은 이벤트는 별도 지구 현황으로 구분한다. 이벤트를 선택하면 지도 위치와 근거 상세가 함께 바뀌고, Forecast 이벤트를 선택하면 같은 지도가 디지털트윈 예측 모드로 전환된다.

8. IA-03 디지털트윈

역할

사건 작업공간 안의 디지털트윈 화면이다. 담당자가 근거 목록이나 타임라인의 예측 이벤트를 누르면 같은 지도가 그 시각의 3D 디지털트윈 화면으로 바뀐다. 독립 페이지가 아니다. 현재 상태와 미래 전망을 구분하고 기준 전망("그대로면?")과 대안 비교("지금·더 빨리 대응하면?")를 한 탭에서 보여 준다. 진행 중 사건의 대응 판단은 이 탭이 끝까지 들고 모의훈련으로 넘기지 않는다 (2026-09-16 · README §2.3. 같은 날 앞선 "[디지털트윈에서 비교]로 넘긴다"를 고친다). 두 전망은 같은 트윈의 결과다.

9. IA-04 대응·실행

역할

10. IA-05 이력 · IA-06 통계

두 메뉴는 같은 사건 원장을 본다. 이력은 사건 한 건을 되짚고, 통계는 여러 사건을 모아 센다. 같은 기간·조건이면 두 화면의 사건 수와 상태가 같다(2026-09-16). 종합상황의 실시간 주요 사건, 모의훈련의 지난 사건 목록도 같은 원장에서 나온다. 목적이 달라 칸은 달라도 사건 수·상태·시각은 갈리지 않는다.

모의훈련의 분석 결과와 분석 보고서는 이력에 쌓지 않는다(2026-09-16). 이력은 "예측 대 실제"를 견주고, 모의훈련은 "실제(재현) 대 바꾼 조건"을 견준다. 분석 결과의 저장·조회·다시 열기·보고서는 모의훈련(IA-07)이 소유한다(03 §26). 개선 항목만은 한 목록이다. 예측 검증과 모의훈련이 찾은 고칠 거리를 출처(검증 · 훈련)만 달리해 모으고, 승인 뒤 반영한다(README §2.3).

진행 중 사건의 판단·승인·조작은 이력에서 하지 않는다. 그 일은 사건 작업공간(IA-02·04)이 한다. 이력은 읽는 자리다.

예측판은 사건을 일으킨 근거의 하나다. 그래서 예측은 ② 발생 근거 안에 관측과 나란히 서고, 그 카드에 실제 결과와 오차를 바로 붙인다. ⑤ 예측 검증은 그 근거가 실제와 얼마나 맞았는지 되짚고 다음 예측·임계치·SOP에 가져갈 것을 남기는 자리다. 오차는 실패가 아니라 학습 재료다(2026-09-16 사용자). 점수·등급은 매기지 않고, 모델 보정·재학습 자동화는 여전히 향후 활용이다(§13.1). 원장이 없는 지난 사건은 아는 것만 선다 — 발생 근거는 당시 상태 값과 예측판, 대응은 실제 대응 목록. 없는 절은 비었다고 말한다.

⑥ 경과는 타임라인이다(CSMS 통합 타임라인 문법 · KISA 이력 탭과 같은 레일). 한 시간축에 두 갈래를 싣는다.

  • 사건 흐름 — 무슨 일이 있었나. 관측·알림·위험 판단·예측판. 둥근 점이고 위험 단계 색을 쓴다.
  • 조치 — 무엇을 했나. 확인·결정·승인·조치·전파·결과. 네모 점이고 종류는 짧은 뱃지로 적는다. 실패와 대체조치는 따로 보이게 한다.
  • 종료 — 체크 아이콘으로 끝을 닫는다. 오탐·병합도 같은 자리에서 닫는다.

수집 이벤트를 전부 늘어놓지 않는다. 사건을 만들었거나 판단·조치가 참조한 이벤트만 선다. 원장에 없는 시각은 지어내지 않는다.

사건 기록 창의 바닥에는 [보고서]가 있으면 그 사건 보고서로 넘어가는 동작, 진행 중이면 [사건 작업공간] 동작이 선다. 창은 한 번에 하나다.

두지 않는 것: 점수·등급·순위, 사건 편집, 이벤트 원장 전체 목록, 대안 분석 결과와 분석 보고서.

보고서는 독립된 업무가 아니라 사건 기록을 바탕으로 생성되는 결과물이다. [보고서] 탭은 그 결과물을 사건을 가로질러 찾는 자리다.

다음은 현재 기준안에서 결정됐다.

  • D0는 IA-01의 감시 우선대상에서 시작하고, D1에 생성된 후보가 실시간 주요 사건에 나타나면 IA-02로 연다.
  • AI 보조는 공통 근거 탐색·요약으로 두며 독립 판단 사일로로 만들지 않는다.
  • 보고서는 IA-05에서 사건 기록으로 생성하는 산출물로 둔다. 이력의 [보고서] 탭이 사건 보고서를 모으고, 분석 보고서는 모의훈련이 소유한다(2026-09-16).
  • 이력(IA-05)과 통계(IA-06)는 별도 메뉴다(2026-09-16). 예측 검증은 사건 한 건의 기록이라 통계에 두지 않고 이력의 사건 기록 창에 이벤트 이력과 함께 둔다. 종합상황·모의훈련·이력·통계의 사건 목록은 같은 사건 원장에서 나오고 사건 수·상태가 같다.
  • P0 자료 확인 전 IA-03은 사전 작성한 시나리오 Forecast로 목표 제품의 흐름을 보여준다. 데이터 구성과 실제 모델 교체 대상은 내부 계약에서 관리하고, 기본 제품 UI에 제작 설명을 넣지 않는다.
  • IA-02는 Phase 1 지구 재난관제와 좌우 패널 골조를 지도 중심 사건 작업공간으로 재편한다. 좌측은 선택한 알림·사건의 관련 이벤트 현황, 우측은 판단·전망과 대응 결과 요약이며 사건 범위는 지점부터 도시 전역까지 수용한다.
  • IA-03 디지털트윈은 독립 페이지가 아니라 사건 작업공간 안에서 예측 이벤트를 눌러 여는 디지털트윈 화면이다. IA-04 대응 승인·실행은 사건 위의 집중 팝업으로 분리한다. 화면 배치와 전환은 04 정본을 따른다.

CUVIA의 디지털트윈은 3D 지도를 뜻하지 않는다.

관측 상태와 기준 데이터를 공간에 정렬하고, 조건을 유지하거나 바꿨을 때의 미래 상태와 영향을 비교해 대응 결정을 지원하는 지도의 상태다. 사건 작업공간 안에서는 그 사건의 예측판(전망 탭)으로 열리고, 모의훈련에서는 지난 사건에서 출발한 시나리오 위에서 열린다. 두 자리가 같은 부품을 쓴다(제2부 · §25).

모든 유형의 트윈은 다음 다섯 질문에 답해야 한다.

  1. 지금 무엇이 관측됐는가?
  2. 현재 조건이 유지되면 언제, 어디까지, 어느 정도 변하는가?
  3. 어떤 조건이나 대응을 바꾸어 비교할 수 있는가?
  4. 사람·시설·도로·지역에 어떤 영향이 예상되는가?
  5. 이 결과는 어떤 데이터·모델·가정으로 만들었고 한계는 무엇인가?

외부 기관이나 협력사 모델이 계산한 결과를 받는 경우에도 CUVIA는 입력 근거, 결과 버전, 사건 연결, 영향 해석과 대응 기록을 관리한다. 자체 계산과 외부 결과 수신을 같은 기능으로 표현하지 않는다.

제품 경험의 방향은 CUVIA 안에서 기준·대안 계산을 요청하고 결과를 비교하는 것이다. 다만 계산 엔진의 기술 소유·운영 주체가 자사인지 협력사인지 현재 자료가 엇갈리므로, 확인 전에는 자사 보유 기술 또는 협력사 제공 기능으로 단정하지 않는다. 실제 결과가 없을 때 사용하는 시나리오 Forecast의 계산 주체와 교체 대상은 내부 계약에서 관리하며, 기본 제품 UI에는 제작 구분이나 면책 문구를 노출하지 않는다.

모의훈련의 유형별 조건 기준안

2026-09-16 /scr-05를 모의훈련으로 재편했다(README §2.3 · §26). 아래 표의 사건·분석 시점·대응·성격은 기준안으로 남긴다. 다만 결과 수치는 §15 경로 표와 §26.4 두 시험을 따른다. 도로 통제·대피·쉼터의 인원·차량 수와 영향 건물 동 수는 결과로 쓰지 않는다. 진행 중 사건(A 서항)의 대안 비교는 사건 작업공간 전망 탭이 맡고, 서항은 종료된 뒤 모의훈련의 지난 사건 목록에 선다. 어느 사건을 Phase 2에 보일지는 README §6.1에서 다시 정한다.

모의훈련(IA §5.2 /scr-05)은 지난 사건 목록에서 사건을 골라 시나리오를 연다(2026-09-16). 대표 데모 A 는 진행 중 사건이고, B~G 는 과거 종료 사건으로 세웠다. 사건마다 원장의 주요 시점 셋 · 실제 대응 · 실제 대응 기준 예측판 · 대응을 일찍 한 대안 예측판을 든다. 대응과 성격은 위 §6~§12의 기준·대안 조건에서 뽑았다. 값은 시나리오 편집값이다. 유형별 장면(지도에 무엇이 어떻게 그려지는가)과 대안의 성격(현상 감소 대 노출 감소)은 제2부 §22가 정한다. 화면에는 재난명(도시침수·하천범람·해안월류·산불·폭염·급경사지·기반시설 장애)을 쓰고 A~G 표현 유형명은 문서용이다.

IA에서의 역할

유형마다 메뉴를 만들지 않는다. 트윈이 쓰이는 메뉴는 사건 작업공간(전망 탭)과 모의훈련 둘이고 유형은 사건이 정한다(2026-09-16 · README §2.3). 진행 중 사건의 기준 전망과 대안 비교는 전망 탭이, 지난 사건에서 조건·대응·유형 결합을 바꿔 돌려 보는 일은 모의훈련이 맡는다(§25·§26). 2026-09-15의 "별도 모의훈련 모드는 없다"와 같은 날 앞선 "디지털트윈 = 사건 기반 대응 What-if"를 고친다. 사건 안에서는 IA 화면이 역할을 나눈다.

유형군에 따라 트윈의 상태 변수·전파·시각화와 판단 항목만 교체한다. 트윈의 유형은 사건이 정한다(§16). 사건 ID, 기준시각, 처리상태, 선택 예측판, 영향공간, 선택 근거와 검토 중 결정은 제품 화면의 사건 맥락으로 유지한다. 사건 시나리오 방식과 이벤트별 dataOrigin·수집·시연 방식은 화면 이동 중 내부 사건 맥락과 계약으로 유지하되, 제작 구분을 위한 표시를 기본 제품 UI에 노출하지 않는다.

README.md §8.3의 대안 분석은 이 문서의 대안 전망 계약을 그대로 사용한다. 진행 중 사건에서 열든 지난 사건에서 열든 계산 계약과 근거·불확실성 구조는 같다. D8 은 기록·검증의 예측 케이스 확정 자리다(IA §13.1). 종료된 사건은 모의훈련의 지난 사건 목록에 선다. 지난 사건을 모의훈련 시나리오로 넘기는 진입점의 Phase 2 포함 여부는 README §6.1에서 정한다.

계산 주체CUVIA 계산·외부 모델 수신·해당 없음실제 모델을 사용할 때 모델·버전·기준시각을 화면에 표시하고 교체 대상은 내부 관리

한 이벤트는 각 축에서 하나의 값을 가진다. 예를 들어 연계 가능 + 재생 + 정상 + 외부 모델 수신처럼 조합할 수 있지만 연계 또는 재생처럼 서로 다른 축을 한 상태값으로 합치지 않는다.

scenarioMode는 이벤트 상태축이 아니라 사건 전체의 현상·예측 데이터 구성 방식이다. 대표 데모에서는 정렬된 과거 재생, 혼합 데모, 완전 모의 중 하나를 선택한다. 혼합 데모는 실제 API·원본 재생·승인 표본·시나리오 데이터를 하나의 기준시각에 맞춰 조합하며, 각 이벤트의 dataOrigin과 ingestionMode를 내부 데이터 계약에 기록한다. 다른 지역·시점의 표본을 사건에 맞게 변환하면 원본 재생이 아니라 합성 데이터 + 모의로 기록한다. 담당자 입력은 ingestionMode=수동, 시연 중 시스템이 실제 생성한 업무 이벤트는 ingestionMode=실시간으로 기록하며 두 경우의 연계 준비도는 내부 생성이다.

합성 입력을 실제 계산 엔진에 넣어 산출했다면 계산 주체와 입력·모델·버전을 기록할 수 있다. 지형에 임의 수위나 형상을 적용해 만든 시각화처럼 검증된 예측 계산이 아니라면 CUVIA 계산이 아니라 해당 없음으로 기록한다. 이 구분과 향후 실제 모델 교체 지점은 fixture·adapter·기획 문서에 남긴다. 기본 제품 UI에는 가상, 더미, 계산 결과 아님 같은 제작 구분이나 면책 문구를 노출하지 않는다. 다만 관측시각·갱신시각·출처기관·모델·버전·데이터 품질처럼 실제 운영 판단에 필요한 정보는 정상적인 제품 정보로 제공한다.

비교 개념은 계산 주체나 수집 방식이 아니라 Phase 2에서 해당 유형을 다루는 문서·표현 역할이다. 계산 결과가 없는 R0 유형은 계산 주체 해당 없음과 역할 비교 개념을 내부에서 각각 구분한다. 표본 사용 승인은 별도 데이터 사용권한 메타데이터이며 ingestionMode 값으로 넣지 않는다.
