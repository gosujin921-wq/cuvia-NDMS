# 창원특례시 안전재난관제 데모
## 기능·정보구조·시연 시나리오 고도화 최종본 v3

> **문서 목적**
>
> 기존 5개 핵심 화면의 구조와 주요 UI는 최대한 유지하면서,
> 조기경보 중심 데모를 **창원시 종합 안전재난관제 데모**로 고도화한다.
>
> 최종 목표는 기능을 많이 보여주는 것이 아니라,
>
> **하나의 재난 사건을 감지 → 확인 → 영향분석 → 선제 대응 판단 → SOP 실행 → 결과 확인 → 사후 검증까지 끝까지 처리하는 흐름**
>
> 을 명확하게 보여주는 것이다.

---

# 1. 최종 방향

## 1-1. 기존 구조는 유지한다

현재 작업된 핵심 요소는 최대한 재사용한다.

- 창원시 전체 지도
- 위험지구 12개
- 수위·강우·변위 센서
- CCTV
- 이벤트
- 상황전파
- 통계 그래프
- 디지털트윈 3D 침수 시뮬레이션

새 시스템을 다시 만드는 것이 아니라,
기존 기능 사이에 **재난 분류 · 판단근거 · 선제 대응 · SOP · 실행결과 · 검증**을 연결한다.

### 기존 인상

> 대시보드 → 지구 → 센서 → CCTV → 전파 → 통계 → 3D

### 최종 인상

> **종합상황**
> → 위험징후
> → **재난관제**
> → 현장·기상·조위 교차확인
> → **디지털트윈**
> → 미래 조건 영향분석
> → **상황대응**
> → 선제 대응 권고
> → 담당자 승인
> → SOP 실행
> → 성공·실패 확인
> → 대체조치
> → **통계·분석**
> → 사후검증

# 2. 최종 IA

핵심 업무 화면은 **5개**를 유지한다.

| 순서 | 기존 메뉴 | 최종 역할명 | 핵심 질문 |
|---|---|---|---|
| 01 | 대시보드 | **종합상황** | 지금 창원시에 어떤 위험이 있고 어디를 먼저 봐야 하는가? |
| 02 | 조기경보 | **재난관제** | 이 지역이 왜 위험한가? |
| 03 | 이벤트·상황전파 | **상황대응** | 확인한 위험에 대해 지금 무엇을 해야 하는가? |
| 04 | 통계 | **통계·분석** | 어떤 재난이 반복됐고 당시 판단과 대응은 어땠는가? |
| 05 | 디지털트윈 | **디지털트윈** | 조건이 악화되면 어디까지 영향을 받을 수 있는가? |

## 보조 기능

| 기능 | 역할 |
|---|---|
| **AI 검색** | 여러 화면의 데이터를 자연어로 질문하고 근거 화면으로 이동하는 보조 기능 |

> **핵심 업무 화면 5개 + 보조 AI 검색** 구조로 정리한다.

# 3. 메뉴 순서와 시연 순서는 다르다

## 평시 메뉴 순서

> 종합상황 → 재난관제 → 상황대응 → 통계·분석 → 디지털트윈

## 실제 데모 시연 순서

> **종합상황 → 재난관제 → 디지털트윈 → 상황대응 → 통계·분석**

디지털트윈은 대응이 끝난 뒤 보는 3D 기능이 아니다.

> **대응을 결정하기 전에 미래 조건의 공간 영향을 확인하는 판단 도구**

로 사용한다.

# 4. 공통 안전재난 분류체계

기존 `내수 · 하천 · 해일 · 저수지`는 재난 종류가 아니라
**위험지구/관제대상 유형**으로 유지한다.

재난 정보는 아래 구조로 별도 관리한다.

> **재난 분야 → 재난유형/위험현상 → 관측타입 → 위험단계**

---

## 4-1. 재난 분야

### 풍수해

- 폭풍해일
- 하천범람
- 내수침수
- 집중호우
- 태풍 등

### 기상·기후

- 폭염
- 열돔

- 강풍
- 대설 등

### 수자원

- 가뭄

- 산사태

- 지반변위 등

---

## 4-2. 분야는 필터, 도넛은 재난유형

재난 분야 4분류는 상위 **필터·그룹핑 축**으로 사용한다.

현재 이벤트 18건을 분야로만 집계하면 풍수해에 대부분 몰리므로,
대시보드와 통계의 재난 분포 도넛은 **재난유형 단위**로 표시한다.

### 현재 18건 재난유형 분포

| 내부 분류값 | 건수 | 화면 표시명 |
|---|---:|---|
| 폭풍해일 | **8** | 폭풍해일 |
| 하천범람 | **3** | **하천범람 위험** |
| 내수침수 | **3** | **내수침수 위험** |
| 집중호우 | **3** | 집중호우 |
| 지반변위 | **1** | 지반변위 |
| **합계** | **18** | |

### 표시명 원칙

`하천범람`과 `내수침수`는 통계·필터용 내부 분류값이다.

현재 이벤트는 수위 임계 초과이지 실제 범람·침수가 확인된 사건은 아니므로
화면에서는:

- `하천범람 위험`
- `내수침수 위험`

으로 표시한다.

반면:

- 폭풍해일
- 집중호우
- 지반변위

는 현재 데모에서 별도 표시 헤지를 두지 않는다.

## 5-3. 주남저수지 변위 분류 원칙

시설 위치가 저수지여도 재난 분류는 **발생 현상**을 기준으로 한다.

| 필드 | 값 |
|---|---|
| 재난분야 | 산지·지반 |
| 재난유형 | 지반변위 |
| 지구유형 | 저수지 |
| 관측타입 | 변위 |

가뭄과 제방 변위를 같은 수자원 재난으로 묶지 않는다.

# 6. 상태축 최종 정의

상태값을 하나의 단계처럼 섞지 않는다.

| 상태축 | 의미 | 주로 보여줄 화면 |
|---|---|---|
| **기상특보** | 외부기관의 특보 | 종합상황 / 재난관제 |
| **계측단계** | 현재 실측값 기준 위험수준 | 재난관제 |
| **조건 시나리오** | 미래 조건에서의 공간 영향 | 디지털트윈 |
| **권고 대응수준** | 시스템이 제시하는 선제 대응안 | 상황대응 |
| **승인 대응등급** | 담당자가 최종 승인한 대응수준 | 상황대응 / 이력 |
| **처리상태** | 담당자의 사건 처리 진행상태 | 상황대응 |
| **도시 대응단계** | 창원시 전체의 대응수준 | 종합상황 |
| **실행결과** | SOP 항목 성공·실패·대체조치 | 상황대응 |
| **최종 이력** | 종료 사건의 전체 결과 | 통계·분석 |

# 7. 기상특보와 시스템 이벤트 분리

같은 `주의보/경보`라는 단어를 사용하더라도
정보 출처를 UI에서 명확하게 구분한다.

### 외부 기상특보

> `기상특보 · 폭풍해일주의보`

### 시스템 이벤트

> `시스템 이벤트 · 서항지구 수위 경보`

뱃지 색·아이콘·출처 라벨을 다르게 사용한다.

특히 S0에서:

- `폭풍해일주의보`
- `서항지구 수위 주의보`

가 동시에 보여도 서로 다른 의미임이 바로 읽혀야 한다.

# 8. 계측단계

현재 센서값이 기준선의 어느 구간에 있는가.

> **주의보 → 경보 → 대피**

서항 예:

> 현재 수위 `3.41 EL.m`  
> 경보 기준 `3.35 EL.m` 초과  
> → **계측단계: 경보**

계측단계는 실제 관측값으로만 결정한다.

---

# 9. 이벤트 처리상태

> **신규 → 확인중 → 대응중 → 종료**

별도 상태변경 버튼을 반복해서 누르게 하기보다
실제 사건 처리 행동과 연결한다.

## 서항 처리상태

| 시각 | 처리 |
|---|---|
| 17:05 | 이벤트 발생 → `신규` |
| 17:07 | 담당자 확인 → `확인중` |
| 17:09 | 주의보 마을방송 |
| 17:16 | **데모 시작 시점 = `확인중`** |
| 17:37 | 대피 대응등급 승인 + SOP 실행 → `대응중` |
| 21:48 | 이벤트 해제 → `종료` |

### 중요

S0에서 서항은 `신규`가 아니다.

17:09에 이미 주의보 마을방송을 했으므로
담당자가 17:07에 한 번 확인한 사건으로 설정한다.

이후 17:22 경보 격상은
**새 사건의 최초 대응이 아니라 기존 사건의 재평가**로 보인다.

---

# 10. 처리 로그 기반 통계

위 처리상태 시각을 사용하면 데모에서:

- 최초 확인시간 `2분`
- 최초 전파시간 `4분`

을 계산할 수 있다.

실제 제품에서는 담당자 처리로그가 수집돼야 하는 항목이지만,
데모에서는 시나리오 데이터로 고정한다.

---

# 11. 도시 대응단계

도시 전체 대응수준은 특정 센서의 계측단계와 별도다.

최종 용어는 기존 문서와 맞춰:

> **상시대비 → 초기대응(보강) → 비상Ⅰ → 비상Ⅱ → 비상Ⅲ**

로 통일한다.

## 데모 상태 전환

- S0~S5: `상시대비`
- **S6 17:37 SOP 승인·실행: `초기대응(보강)`**
- S7~S8: `초기대응(보강)` 유지

비상Ⅰ·Ⅱ·Ⅲ은 이번 메인 데모에서는 실제 발생시키지 않는다.

도시 대응단계는 자동 판정 기능으로 설명하지 않고
**시연 시나리오 상태값**으로 사용한다.

---

# 12. 미래 위험 표현 원칙

실제 예측모델이 확정되지 않은 상태에서 아래 표현을 사용하지 않는다.

- AI가 미래 수위를 예측
- 시스템이 19:10에 4.24m를 예측
- 침수 발생확률
- 예측 정확도

대신:

> **현재 관측값 + 공식 미래 조건 + 시나리오 가정**

을 이용한 **조건 시뮬레이션**으로 표현한다.

# 13. 서항 만조 조건 시나리오

## 현재 상태

> 현재 계측  
> `경보 · 3.41 EL.m`

## 조건 정보

> `19:10 만조 조건`

판단근거 예:

- 천문조
- 현재 해일 편차
- 강우 지속조건
- 현재 수위
- 폭풍해일특보

## 조건 시나리오

> **만조 조건 시나리오 · 4.24 EL.m**  
> 대피 기준 `4.20 EL.m` 초과

## 시스템 역할

> **선제 대응 권고 · 대피**

## 담당자 역할

> **[대응등급 대피로 상향]**

담당자가 승인한 뒤에야
`승인 대응등급 = 대피`가 확정된다.

# 14. 권고 대응수준과 승인 대응등급 분리

## 17:34

아직 담당자가 승인하기 전.

> 현재 계측 `경보 3.41m`  
> 만조 조건 시나리오 `4.24m / 대피 기준 초과`  
> **권고 대응수준 `대피`**

## 17:37

담당자가:

> **[대응등급 대피로 상향]**

승인.

이 시점부터:

> **승인 대응등급 = 대피**

가 사건 데이터에 남는다.

이후:

- SOP
- 상황전파 문안
- 대응 이력
- 대응 통계

는 승인 대응등급을 따른다.

---

# 15. 계측단계와 승인 대응등급은 동시에 유지

17:37~19:22의 서항은:

> **계측단계 = 경보**  
> **승인 대응등급 = 대피**

다.

둘을 하나로 합치지 않는다.

## 지도 표현

- 수위 이벤트 핀: **주황색 `경보` 유지**
- 별도 배지: **`대피 대응중`**

대응등급이 대피라고 해서
센서가 이미 대피 기준을 넘은 것처럼 빨간 계측 핀으로 바꾸지 않는다.

19:22 실측 수위가 실제 대피 기준을 넘었을 때
계측단계가 대피로 바뀐다.

---

# 16. SOP 대응 체계

SOP는 별도 메뉴를 만들지 않고
**상황대응 화면 안에 포함**한다.

기본 흐름:

> 선제 대응 권고  
> → 담당자 대응등급 승인  
> → 해당 등급 SOP 표출  
> → 자동 처리 확인  
> → 승인 후 실행  
> → 실행결과 확인  
> → 실패 시 대체조치 기록

---

# 17. `자동 처리`와 `승인 후 실행`

기존 `자동 / 수동` 표현은 다음으로 통일한다.

## 자동 처리

> **담당자의 사전 승인이 필요 없는 처리**

자동이라고 해서 확인하지 않아도 되는 것은 아니다.

실행 후 반드시 결과를 확인한다.

예:

- 이벤트 기록
- 격상 이력 저장
- 담당부서 알림
- CCTV 집중감시 전환
- 대응등급 확정 후 상급기관 자동보고

## 승인 후 실행

담당자의 명시적인 승인 이후 시스템이 실행하는 조치.

예:

- 주민 재난문자
- 마을방송
- 전광판
- 도로 차단 요청
- 대피소 개방 요청

사람이 각 채널을 직접 수행한다는 의미가 아니라:

> **담당자 승인 → 시스템 실행**

구조다.

---

# 18. 단계별 전파 규칙 정합성

전파 기본수단은 단계에 따라 일관되게 적용한다.

| 대응수준 | 기본 전파 |
|---|---|
| **주의보** | 마을방송 |
| **경보** | 재난문자 + 마을방송 |
| **대피** | 재난문자 + 마을방송 + 전광판 |

로고젝터는 기본선택에서 제외하고
필요 시 담당자가 추가하는 선택수단으로 둔다.

### 서항 사건

17:09:

> 주의보 · **마을방송**

17:37:

> 선제 대피 대응 승인  
> → **재난문자 + 마을방송 + 전광판**

같은 사건 안에서 대응 범위 확대가 보이도록 한다.

---

# 19. 해일 SOP 예시

| 항목 | 실행 방식 | 주의보 | 경보 | 대피 |
|---|---|---|---|---|
| 이벤트 기록·격상 이력 저장 | 자동 처리 | ● | ● | ● |
| 담당부서 알림 | 자동 처리 | ● | ● | ● |
| 관련 CCTV 집중감시 | 자동 처리 | ● | ● | ● |
| 마을방송 | 승인 후 실행 | ● | ● | ● |
| 주민 재난문자 | 승인 후 실행 | — | ● | ● |
| 전광판 | 승인 후 실행 | — | — | ● |
| 해안도로 차단·대피소 개방 요청 | 승인 후 실행 | — | — | ● |
| 상급기관 상황보고 | 자동 처리 | — | ● | ● |

### 상급기관 보고

`자동 처리`는 별도 승인이 필요 없다는 뜻이다.

대응등급이 확정된 뒤 자동으로 연계가 실행되고,
그 결과는 반드시 확인한다.

따라서 S6 승인 뒤 상급기관 자동보고가 실행되고,
S7에서 연계 실패를 발견하는 흐름이 성립한다.

# 20. SOP 실행결과와 실패 처리

SOP는 실행 버튼에서 끝나지 않는다.

각 실행항목에:

- 성공 / 실패
- 실행시각
- 대상
- 접수기관
- 처리결과
- 실패사유

를 표시한다.

## 서항 예시

> ✓ 주민 긴급 재난문자 · 412명  
> ✓ 마을방송·전광판  
> ✓ 해안도로 차단·대피소 개방 요청  
> ✕ 경상남도 재난안전상황실 자동보고 · 연계 끊김

### 실패 대체조치

> `경상남도 재난안전상황실 자동보고 실패`  
> `연계 끊김 · 09:02~`  
> **[유선 보고 기록]**

대체조치 후:

> `17:39 유선 보고 · 경상남도 재난안전상황실 당직`

을 동일 사건 이력에 이어 붙인다.

# 21. 지도와 3D 원칙

## 핵심

> **3D는 표현 방식이고, 디지털트윈은 분석 방식이다.**

제품적으로는 재난관제에서도 3D 사용이 가능하다.

하지만 **메인 데모에서는 재난관제를 2D로 고정**한다.

> 2D 현재 관제

이라는 시각적 변화가 Twin의 역할을 더 강하게 보여주기 때문이다.

이번 데모에서 자체 계산·판정하지 않는다.

배경 정보 수준으로 제한한다.

이번 데모 범위에 넣지 않는다.
