>
> 기준일: 2026-09-11
>
> 역할: Phase 2의 목표, 조사 기준, 산출물, 작업 순서와 의사결정 상태를 관리하는 상위 계획 문서

## 1. 이 문서의 역할

이 README는 상세 요구사항을 모두 담는 문서가 아니다. Phase 2에서 무엇을 왜 조사하고, 어떤 순서로
설계·구현하며, 무엇이 결정됐고 무엇이 남았는지를 관리하는 **마스터 플랜**이다.

세부 내용은 이 계획에 따라 별도 문서에서 작성한다. 같은 내용을 여러 문서에 반복하지 않으며,
README에는 확정된 방향, 문서 간 관계, 진행 상태와 결정 관문만 유지한다.

## 2. Phase 2의 목적

Phase 2는 현재 구현을 정답으로 두고 기능과 재난유형을 계속 추가하는 작업이 아니다.

> **원본 자료와 추가 조사 결과를 기준으로 CUVIA의 제품 방향을 새로 설계하고, 여러 이벤트를 하나의
> 재난 사건으로 해석해 디지털트윈 예측과 대응에 활용하는 방식을 대표 데모로 증명한다.**

이 데모는 한 가지 목적만 가진 시제품이 아니다. 영업 현장에서는 CUVIA가 지향하는 제품 경험과 차별점을
설득력 있게 보여주고, 내부에서는 기획·디자인 의도를 검증하며, 이후 개발자가 같은 코드와 정보구조 위에
실제 API·모델·업무 연계를 교체·확장할 수 있는 **비전 데모이자 실개발 출발점**이다. 따라서 운영 제품의
모든 기능을 완성하는 것이 목표는 아니지만, 화면과 상호작용은 실제 제품으로 이어질 수 있게 설계한다.

이번 단계에서 답해야 할 핵심 질문은 다음과 같다.

1. CUVIA는 어떤 원천 데이터와 이벤트를 수집하는가?
2. 서로 다른 이벤트를 어떤 기준으로 하나의 재난 사건에 연결하는가?
3. 사건 유형에 따라 디지털트윈의 입력, 시간축, 공간 표현과 결과가 어떻게 달라지는가?
4. 예측 결과가 담당자의 판단, SOP, 전파, 조치와 기록으로 어떻게 이어지는가?
5. 이 방향을 한 건의 대표 사건으로 어떻게 이해하기 쉽게 시연할 것인가?

### 2.1 Phase 2를 끌고 갈 핵심 제품 흐름

개별 기능의 수가 아니라 다음 흐름이 CUVIA Phase 2의 중심이다.

```text
센서·시설·공공/기관 API·CCTV/VLM
    ↓ 수집·정규화
원천·파생·분석 이벤트
    ↓ 시간·공간·의미·품질 결합
위험도 매트릭스 판단 + 디지털트윈 예측 영향
    ↓ 위험등급·기여 근거·예상 영향
복합 알림과 사건 후보
    ↓ 담당자 확인
사건 확정·현재 판단·기준/대안 전망
    ↓
SOP 권고·승인·전파·조치·결과 확인
    ↓
사건 타임라인·보고서 자동 생성·예측 검증
```

센서 임계치, API 특보, VLM 분석과 디지털트윈 예측은 각각 독립된 근거 이벤트다. 위험도 매트릭스는
수위·강우·영상 맥락과 시설·예측·품질 정보를 다지표로 결합해 위험등급과 지표별 기여 근거를 계산한다.
시스템은 매트릭스 기준 또는 사전에 정한 단일 심각·복합 조건이 충족되면 담당자가 확인할 복합 알림과
사건 후보를 자동 생성할 수 있다. 사건 확정, 대외 전파, 시설 제어와 도시 대응단계 변경은 담당자·승인자의
결정으로 남긴다.

`이벤트 발생`, `담당자 알림`, `사건 후보 생성`, `도시 대응단계 변경`은 같은 상태가 아니다. 알림은
이벤트·Forecast의 조합을 사람이 검토할 업무 신호로 바꾼 것이며, 사건 후보는 그 근거를 묶어 처리상태와
담당을 갖게 한 Incident다. 이 구분과 전체 흐름이 개별 화면·기능보다 우선한다.

## 3. 설계 출발점

### 3.1 새로 설계한다

- 현재 `designs/src`는 Phase 1 프로토타입이며 Phase 2 목표 사양이 아니다.
- 기존 화면과 코드는 재사용 가능성을 판단하기 위한 현황 자료로만 사용한다.
- 기존 구현의 메뉴, 화면 번호, 데이터 구조와 시나리오를 그대로 유지하는 것을 목표로 삼지 않는다.
- 원본 자료와 추가 조사에서 확인된 문제, 사용자 업무, 데이터와 기술 근거를 먼저 정리한 뒤 구조를 설계한다.
- 조사 결과 기존 방향이 적절하지 않으면 화면 내부뿐 아니라 IA와 업무 흐름도 재편할 수 있다.

### 3.2 백업 문서의 위치

`docs/레거시/고도화_백업/`은 삭제 전 자료를 보존하기 위한 **복구용 사본**이다.
`docs/레거시/작업/`은 정본 반영이 끝난 초안과 과거 작업 문서를 보존하는 **작업 이력**이다.

- 새 설계의 출발점이나 근거 문서로 사용하지 않는다.
- 백업 문서의 분류, 수량, 결론과 표현을 새 문서에 자동 승계하지 않는다.
- 원본에서 다시 확인할 수 없는 내용은 근거로 채택하지 않는다.
- 사용자가 별도로 요청하지 않는 한 백업 문서를 검토 대상으로 포함하지 않는다.
- `레거시/작업/`의 문서는 작성 당시 판단을 보존하므로 현재 정본과 충돌할 수 있다. 새 설계의 근거나
  활성 요구사항으로 인용하지 않고, 필요할 때 변경 이력 확인에만 사용한다.

## 4. 근거 자료 원칙

### 4.1 근거 우선순위

설계 판단은 다음 순서로 근거를 확인한다.

1. **사업·실증 원본:** 발주처 자료, 완료보고서, 실제 연계 명세와 운영 자료
2. **공식 표준·공공 근거:** 정부 정책, 국제 표준, 공공기관 기술·운영 지침
3. **자사 원본:** CUVIA 제품 소개서와 제안 자료
4. **타사·협력사 원본:** 경쟁 제품과 협력 범위 파악을 위한 자료
5. **현재 구현:** Phase 1이 실제로 보여주는 범위와 재사용 가능성 확인

제안서에 적힌 기능, 회사가 보유한 기술, 파트너가 제공할 기능, 현재 데모에 구현된 기능과 Phase 2에서
새로 만들 기능을 문서와 대외 설명에서 같은 상태로 취급하지 않는다. 이 구분은 기획 문서·데모 데이터
구조·필요 시 대외 설명에서 관리한다. 데모 화면은 목표 제품의 사용자 경험으로 만들며 `가상`, `더미`,
`계산 결과 아님` 같은 제작 사정이나 면책 문구를 기본 UI에 노출하지 않는다.

### 4.3 추가 조사 기준

추가 조사는 단순히 경쟁사 화면을 더 모으는 작업이 아니다. 아래 다섯 축에서 공식 자료와 실제 적용
사례를 찾아 제품 구조의 근거를 보강한다.

| 조사 축 | 확인할 내용 | 설계에 반영할 대상 |
|---|---|---|
| 이벤트 수집 | 센서·영상·기상·시설·기관 데이터의 식별자, 위치, 시각, 품질과 갱신 | 공통 관측 이벤트 모델 |
| 사건 전환 | 중복 제거, 시간·공간 연결, 원인·파생 관계, 사람 확인 | 사건 생성·병합·종료 규칙 |
| 예측·트윈 | 현재 상태, 기준 전망, 대안 조건, 영향 범위와 불확실성 | 유형별 디지털트윈 계약 |
| 대응·전파 | 심각도·긴급도·확실성, 승인, SOP, 채널별 결과 | 대응 실행과 전파 모델 |
| 기록·검증 | 입력 근거, 판단, 예측 버전, 실제 결과와 오차 | 타임라인·보고서·사후 검증 |

현재 상세 설계에 채택한 공식 출발점은 다음과 같다.

- [CloudEvents](https://github.com/cloudevents/spec/blob/main/cloudevents/spec.md): 출처가 다른 이벤트의
  공통 식별·출처·유형·시각·대상 봉투
- [OGC SensorThings API](https://www.ogc.org/standards/sensorthings/): 서로 다른 IoT 시스템의 장비,
  센서, 관측값과 위치를 일관된 구조로 다루기 위한 기준
- [OGC API EDR](https://docs.ogc.org/is/19-086r6/19-086r6.html): 위치·영역·경로·시간 기반 환경 데이터 조회
- [ETSI NGSI-LD](https://cim.etsi.org/NGSI-LD/official/introduction.html): 시설·구역·사건의 속성·관계·시간 변화
- [OASIS Common Alerting Protocol 1.2](https://www.oasis-open.org/standard/cap/): 경보의 식별자,
  심각도, 긴급도, 확실성, 대상 지역, 갱신과 취소를 표현하는 기준
- [ISO 22320:2018](https://www.iso.org/standard/67851.html): 역할·책임·업무·자원과 기관 간 공동 대응
- [WMO Early Warnings for All](https://wmo.int/all-activities/build-resilience/early-warnings-all):
  위험지식에서 관측·예측·전파·대응까지 이어지는 종단 흐름
- [NIST AI RMF 1.0](https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-ai-rmf-10):
  AI 결과의 신뢰성·설명가능성·책임성과 사람의 확인·승인 경계

추가 자료를 채택할 때는 발행기관, 문서명, 버전 또는 기준일, 적용한 결정과 한계를 함께 기록한다.
검색 결과나 홍보 문구만으로 제품 기능을 확정하지 않는다.

## 5. 설계 원칙

- **사건 중심:** 센서나 기능 목록보다 담당자가 판단하고 대응할 사건이 중심이다.
- **원천과 판단 분리:** 수집값, 관측 이벤트, 시스템 판단, 담당자 확인을 구분한다.
- **현재와 미래 분리:** 현재 관측, 조건 유지 전망, 대안 전망과 실제 결과를 구분한다.
- **공통 골격과 유형별 차이:** 업무 흐름은 공통으로 두고 트윈의 입력·표현·결과는 유형별로 설계한다.
- **사람 승인:** AI와 예측은 근거와 권고를 제공하며 되돌리기 어려운 조치는 담당자가 확정한다.
- **근거 추적:** 화면의 판단과 예측 결과는 사용한 데이터, 시각, 출처와 가정으로 돌아갈 수 있어야 한다.
- **데모 데이터는 내부에서 구분:** 실제 API·원본·승인 표본·시나리오 데이터·사용자 입력과 계산 주체는
  데이터 계약·fixture·adapter·기획 문서에서 구분해 실제 연계로 교체할 수 있게 한다. 기본 UI에는 이
  제작 구분을 상태 칩이나 면책 문구로 노출하지 않는다. 관측시각·갱신시각·출처기관·모델 버전처럼 실제
  제품 판단에 필요한 정보만 해당 화면의 근거로 표시한다.
- **혼합 데모:** 확보 가능한 실제 API·원본 재생·승인 표본은 쓰고, 확보하지 못한 내부 연계는 시나리오
  데이터로 채운다. 하나의 사건 기준시각을 유지하고 이벤트별 원본시각·시나리오시각·교체 대상은 내부
  데이터 계약과 02 §5.4에 기록한다. 화면은 하나의 제품 경험으로 연결하되 검증하지 않은 정확도·운영 실적을
  실제 성과로 대외 주장하지 않는다.
- **대표 데모 집중:** 모든 유형의 전체 흐름을 구현하지 않고 한 사건으로 깊이를 증명한다.
- **시연 우선 연결:** 데모는 제품 방향을 확인하는 시연이다. 화면 완성도가 아니라 기획 문서와 끊김 없이
  연결되는지를 기준으로 삼고, 합성 데이터는 같은 이벤트 계약과 사건 기준시각을 따른다.
- **수량 비목표:** 화면, 사건, 재난유형 수를 Phase 2의 성과로 삼지 않는다.

## 6. 문서 구조와 역할

활성 고도화 문서는 아래 범위로 제한한다.

### 6.1 문서 작성 운영 순서

핵심 문서는 다음 순서를 한 묶음으로 진행한다.

```text
작성 → 검수 → 검토 → 보완
```

| 단계 | 목적 | 결과물·처리 원칙 |
|---|---|---|
| 작성 | 원본과 공식 근거를 바탕으로 해당 정본의 기준안을 만든다 | 내용은 `01~03` 또는 IA MD에 작성한다 |
| 검수 | 문서가 자기 질문에 답하는지, 다른 정본·원본과 충돌하는지 독립적으로 찾는다 | `검수/`에 대상 버전과 근거가 명시된 점검 기록을 남기며 원문은 고치지 않는다 |
| 검토 | 검수 지적을 현재 문서와 다시 대조해 `채택·부분 채택·보류·기각`으로 판단한다 | 지적을 자동 수용하지 않고 판단 근거를 확인한다 |
| 보완 | 검토에서 채택된 내용만 정본에 반영하고 연관 문서의 상태를 맞춘다 | 새 보완 문서를 만들지 않고 대상 정본을 갱신한다 |

- `검수/` 문서는 제품 방향이나 요구사항의 정본이 아니라 특정 시점 문서에 대한 점검 기록이다.
- 검수 기록은 대상 파일의 판본·기준일 또는 줄 수를 명시한다. 원문이 바뀌면 남은 지적도 현재 판본에
  다시 대조한다.
- 검수와 검토 단계에서는 원문을 동시에 수정하지 않는다. 무엇을 반영할지 결정한 뒤 보완 단계에서만
  정본을 수정한다.
- 보완 후에는 README와 연관 상세 문서, IA MD, 엑셀 동기화본에 파급된 상태만 확인한다.
- 검수 결과를 설명하는 별도의 `최종안·보완안·재검토안` 문서를 추가로 만들지 않는다.
- 한 묶음이 끝난 뒤 중요한 구조 변경이 있으면 같은 순서로 다시 검수한다.
- `초안/` 작업메모는 미확정 사항을 잠시 정리할 때만 허용한다. 채택한 내용은 주제 소유 정본에 옮기고,
  보류한 확인사항은 해당 정본의 `남은 확인`에 기록한 뒤 같은 작업 묶음에서 `docs/레거시/작업/`으로
  이동한다. 명시적인 삭제 요청이 없으면 초안을 삭제하지 않는다. 이동한 초안은 작업 이력일 뿐 정본의
  참고 자료나 근거로 사용하지 않는다.

### 6.2 전체 시각화 HTML 운영 원칙

`overview.html`은 흩어진 정본을 한눈에 검토하기 위한 **읽기 전용 시각화 뷰어**다.

- 제품 아키텍처, 이벤트→사건 전환, 대표 데모 D0~D8, 화면, 공통 정보 객체와 데이터 준비도를
  다이어그램과 요약으로 보여준다.
- 제품 아키텍처는 새 구성요소를 정의하는 설계가 아니라 §6 소유 문서의 관계와 01의 객체·이벤트 흐름을
  시각화한 것이다.
- 새로운 요구사항·수치·결정을 HTML에서 만들지 않는다.
- 상세 내용을 복제하지 않고 각 근거 문서와 해당 절로 이동하는 링크를 제공한다.
- HTML과 MD가 다르면 마스터 플랜과 해당 상세 MD가 우선한다.
- 별도 HTML을 계속 추가하지 않고 `overview.html` 한 파일만 유지한다.
- 상세 문서와 IA 검토가 끝난 뒤 작성하고, 최종 교차검수에 사용한다.

## 7. 작업 순서와 결정 관문

### 0단계 · 마스터 플랜 확정

- 이 README에서 목적, 근거, 산출물과 작업 순서를 확정한다.
- 루트 README와 `CLAUDE.md`가 이 문서를 Phase 2 계획으로 가리키는지 확인한다.
- 백업과 활성 문서의 역할을 분리한다.

완료 관문: 무엇을 조사하고 어떤 문서를 어떤 순서로 만들지 한 문서에서 확인할 수 있다.

### 1단계 · 원본 분석과 추가 조사

- 확보한 자사·사업·타사·협력사 원본을 목적별로 분석한다.
- 공식 표준과 공공 정책·적용 사례를 추가 조사한다.
- 사실 주장은 출처·페이지와 `확인·부분 확인·미확인`을 구분하고, 제품 설계 판단과 가정은 사실처럼
  표현하지 않는다.
- 현재 보유, 파트너 연계, Phase 2 계획과 장기 후보를 분리한다.

완료 관문: 핵심 제품 결정에 출처가 있고, 문서·대외 설명에서 근거 없는 기능을 보유 기능처럼 쓰지 않는다.

### 2단계 · 이벤트·사건 모델

- `01_이벤트·사건모델.md`를 작성한다.
- 수집원별 이벤트와 필수 메타데이터를 정의한다.
- 센서·API·VLM·Forecast를 단일·복합 조건으로 평가해 어떤 알림을 만들고 언제 사건 후보로 올리는지 정의한다.
- 관측 이벤트가 사건 후보가 되고 확인·병합·종료되는 규칙을 정의한다.
- 지점·시설·회랑·구역·전역 범위와 원인·파생 사건 관계를 정의한다.

완료 관문: 대표 사건 하나가 어떤 원천 데이터에서 만들어졌는지 역추적할 수 있다.

### 3단계 · 대표 데모 시나리오

- 후보 사건을 데이터 가용성, 설명력, 트윈 차별성, 대응 연결성으로 비교한다.
- 대표 사건 한 건을 확정하고 `02_대표데모시나리오.md`를 작성한다.
- 수집부터 사건화, 예측, 승인, 실행, 결과 기록까지 시연 흐름을 확정한다.
- 실연계·계산·시나리오 데이터는 내부 계약과 기획 문서에서 구분하고 화면에서는 동일한 제품 문법으로 표현한다.

완료 관문: 한 사건만으로 CUVIA가 수집한 이벤트를 어떻게 활용하는지 설명하고 시연할 수 있다.

### 4단계 · 유형별 디지털트윈

- 재난유형을 무작정 늘리지 않고 트윈의 계산·표현 방식이 달라지는 유형군을 먼저 정의한다.
- `03_유형별디지털트윈.md`를 작성한다.
- 유형별 대표 사건, 입력, 시간축, 공간 표현, 영향 결과와 대응 활용을 정의한다.
- 데이터나 모델이 없을 때의 대기·대체 표현도 함께 설계한다.

완료 관문: 전체 시나리오를 중복 구현하지 않아도 유형별 트윈 차이를 설명할 수 있다.

### 5단계 · IA와 데모 범위 확정

- 상세 문서의 기준안을 `CUVIA_NDMS_기능및정보구조도.md`에 업무·정보구조로 변환한다.

- I1의 URL과 예외 처리는 IA §5.2, D8의 훈련 전달 계약은 IA §13.1을 따른다.
- 실제 API는 확보되는 대로 붙이고 나머지는 같은 계약의 시나리오 데이터로 채운다. 02 §5.4 표가 기준이다.
- 원본 자료, 대외 설명, 상세 설계와 실제 데모를 다시 대조한다.
- 예측 근거, 승인 경계, 실패·대체조치와 한계를 검증한다.

완료 관문: 기획 문서와 데모가 동일한 제품 방향과 기능 상태를 말한다.

- 전체 흐름은 대표 사건 한 건으로 깊게 보여준다.
- 나머지 유형은 대표 사건과 디지털트윈의 차이를 보여준다.
- 현재 코드는 Phase 1 현황과 재사용 가능성을 확인하는 자료다.
- 백업 문서는 복구용이며 새 설계의 근거로 사용하지 않는다.

- 재난유형은 행정 명칭을 나열하지 않고 계산·시간·공간·판단 방식이 다른 트윈 유형군으로 설계한다.
- 사건 확인 전 자동화는 내부 수집·정규화·분석·검토 알림으로 제한하고 외부 전파·시설 제어는 담당자가
  승인한다.
- 외부 NDMS 사건은 원본 식별과 변경 이력을 보존하며 CUVIA 사건과 자동 병합하지 않는다.
- 실제 원격제어는 Phase 2 대표 데모에서 제외하고 시설 요청·승인·결과 확인까지만 표현한다.
- VLM은 사건 근거와 감시 우선순위를 제공하며 사람의 사건 확정과 대응 승인을 대신하지 않는다.

### 8.2 확정된 데모 방향 (2026-09-10 사용자 결정 · 2026-09-14 화면 검토 반영)

- 대표 데모는 원본 근거가 가장 강한 `창원 도시침수`를 우선안으로 두고, `서항`은 실제 배수권역·센서·시설
  매핑을 확인할 우선 적용 후보로 둔다.
- 비교 유형은 해안 경계·월류, 이동 전선·확산, 지반·구조 영향을 유지한다. 기반시설 장애는 독립 업무가
  필요할 때 별도 사건으로 만들며 다른 사건의 `악화` 또는 `파생` 관계로 공통 적용한다.
- 대표 데모는 `혼합 데모`를 기본으로 하며 실제 API·원본·승인 표본을 우선 사용하고 미확보 내부 연계만
  같은 이벤트 계약의 시나리오 데이터로 보완한다.
- C·D·F는 IA-03 유형 전환으로 제시한다. C는 Phase 1 서항 자산과 사전 작성한 시나리오 Forecast로 시간
  조절·대안 선택이 동작하는 예측 화면을 보여주는 I4 선택 확장이다. 계산 주체와 실제 모델 교체 대상은
  내부에서 관리하고 준비도는 R1을 유지한다. D·F는 I4의 R0 정적 개념
  예시로 표현한다. D의 대표 사례는 산불이다. B는 확장 설계, E는 장기 후보,
  G는 공통 악화·파생 설계로 유지한다.
- IA-02는 Phase 1 지구 재난관제를 범위가 유동적인 지도 중심 사건 작업공간으로 재편한다. 좌측은 관련
  이벤트, 우측은 판단·전망과 대응 결과 요약을 보여준다. **대응 승인·실행은 별도의 집중 팝업으로 분리**하고
  열린 동안 조작은 팝업 한 곳에서만 한다. 2026-09-14 화면 검토로 앞선 `우측 대응 패널 기본` 안을 대체했다.
  화면 연결과 배치 기준은 `04_사건작업공간_화면상세.md`가 소유한다. IA-05는 독립 페이지로 두고
  상시 접근 가능하되 대표 데모에서는 D8에 진입한다.
- 2026-09-14 화면 검토 결정. 대응 집중 팝업의 SOP는 CSMS SOP 대응 탭 구조(우선순위 MUST·SHOULD·MAY 그룹, 자동·수동
  두 축, 대응 흐름 4단계 `상황실 관제 · 담당기관 · 주민 전파 · 현장 조치`, 주민 전파 한 항목)를 따른다. 내부 자동 조치는
  사건 후보 생성 시 완료하고 대외 전파·시설 요청은 승인 뒤 실행한다. 긴급 시 판단·전망 없이 같은 팝업으로 진입한다. 통제
  전환은 실행 결과 도착 뒤 가능하며 필수 조치 게이트는 종료에 둔다. 디지털트윈은 IA §8대로 사건 화면 안에서 같은 지도가
  바뀌며 `/scr-05`는 사전 조건분석·훈련 실행 경로로 남긴다.
- 예측 결과는 사건의 Forecast로 저장되고, E8의 `FORECAST_UPDATED`가 생성·갱신된 Forecast를 참조한다.
  큐·근거 목록·타임라인에는 갱신 이벤트가 한 줄로 서고, 누르면 연결된 Forecast를 보여주는 같은 지도의
  3D 예측 화면으로 바뀐다. 담당자가 고른 시각·대안이 대응 권고에 반영된다.
- 대응 모의훈련은 사이드바 메뉴로 설계하되 D0~D8 대표 사건의 필수 동선에는 넣지 않는다. 우선 D8의
  `이 사건으로 훈련 시나리오 만들기` 진입점을 연결하고, 일정이 허용하면 A 도시침수 시나리오 목록·실행을
  영업 시연용 에필로그로 구현한다. 편집·예약과 C 유형 훈련은 후속 범위다. 실행 화면은 Phase 1 트윈
  페이지의 사전 조건분석 구조를 재사용한다. D8에서는 원 사건·조건 이벤트·E8이 참조한 선택 Forecast·
  판단·대응 이력을 고정 스냅샷으로 묶어 TrainingScenario를 만들고, 훈련 결과는 원 사건을 바꾸지 않는
  별도 TrainingRun으로 기록한다.
- Phase 2는 신규 URL을 만들지 않고 기존 `/scr-*` 라우트를 유지한다. 사건 중심 재편은 기존 화면 안의
  정보 구조와 패널 역할을 바꾸는 것이며, 사건·Forecast 선택은 화면 상태와 기존 query 전달 방식을
  우선 사용한다. 잘못된 선택값을 임의의 최신 사건·Forecast로 자동 대체하지 않는다.
- 펌프 장애가 독립 고장 기준을 넘을 때 별도 사건으로 분리하는 관계 모델은 유지하고, 관계선 장면은
  I4에서 선택 구현한다.

C 모의 예측과 G 파생 장면은 제품 방향에는 포함하지만 대표 도시침수 D0~D8의 완료 조건에는 넣지 않는
I4 선택 범위로 확정한다. D8의 TrainingScenario 생성 진입점과 전달 계약은 필수다.

위 항목은 구현 범위의 기준이다. P0 자료가 확보되면 값과 데이터만 같은 이벤트 계약으로 교체하고 방향은
바꾸지 않는다. 대외적으로 보유·실증 기능이라고 설명할 때는 §4.1의 구분을 따른다.

### 8.3 혼동하지 않을 세 가지 개념

| 용어 | 의미 | 이번 데모에서의 위치 |
|---|---|---|
| 시나리오 데이터 | 실제 API·원본이 없는 이벤트를 같은 계약과 사건 시각에 맞춰 만든 데모 데이터 | D0~D8에 사용하되 제작 구분은 내부에서 관리 |
| 대응 모의훈련 | 대응 이력으로 훈련 시나리오를 만들고 의사결정·실행을 연습하는 E-SOP 업무 | D8 진입점은 포함, 목록·실행은 일정이 허용할 때 에필로그로 구현 |
| 사전 조건분석 | 사건 또는 훈련 조건을 바꿔 트윈에서 예상 변화를 비교하는 what-if 분석 | 사건 트윈과 A 유형 훈련 실행 화면이 같은 구성요소를 재사용 |

시나리오 데이터는 구현 재료, 대응 모의훈련은 업무 과정, 사전 조건분석은 트윈의 분석 방식이다. 세 용어를
서로 바꾸어 쓰지 않으며, 첫 번째 항목은 제품 UI의 사용자 문구가 아니다.

이 문서에서 `P0`는 대표 사건과 시연 방식 자체를 결정하는 필수 자료 확인, `P1`은 시연의 구체성과
신뢰도를 높이는 확인, `P2`는 사후검증 강화 자료를 뜻한다. `검토`는 검수 지적의 채택 여부를 판정하는
단계이고, `사용자 결정`은 제품 방향·화면 방식처럼 문서만으로 확정할 수 없는 선택을 뜻한다.

## 9. IA 재편 기준안

Phase 2 IA 기준안은 [`CUVIA_NDMS_기능및정보구조도.md`](./CUVIA_NDMS_기능및정보구조도.md)에서
관리한다. 이 문서에는 다음 상위 원칙만 유지한다.

- 담당자의 질문을 기준으로 `종합상황 → 사건 작업공간(디지털트윈 포함) → 대응·실행 → 기록·검증`의 업무
  공간과 `대응 모의훈련` 메뉴를 연결한다.
- AI는 공통 근거 탐색·요약 보조로 두고, 보고서는 사건 기록에서 생성되는 산출물로 둔다.
- 운영 관리는 제품 구조에 포함하되 대표 데모 주동선과 분리한다.
- 기존 화면은 수량으로 승계하지 않고 `유지·재편·통합·제외·보류`로 판정한다.
- 화면·패널 수가 아니라 대표 사건의 판단과 행동이 끊김 없이 이어지는지를 완료 기준으로 사용한다.
- 사건 작업공간은 한 현장을 뜻하지 않는다. 같은 원인·영향·대응으로 관리할 업무 범위를 지점·시설·구역·
  지구·도시 전역까지 수용하고, 독립 대응이 필요한 지역·시설은 연관 사건으로 분리한다.

`CUVIA_NDMS_기능및정보구조도.xlsx`는 위 IA MD를 10개 시트로 옮긴 검토용 동기화본이다. 별도의 결정을
추가하지 않으며 값이 다르면 MD가 우선한다. `Phase1판정` 시트만 기존 화면의 재사용·재편 판단을 담는다.

## 10. 외부 확인이 남은 항목

제품 방향과 화면 방식은 §8.2로 닫혔다. 아래는 기관·협력사·공식 자료에서 받아야 닫히는 것이고, 구현을
막지 않는다. 확보되면 시나리오 데이터와 내부 연계 구성을 실제 데이터·모델로 교체한다.

- 대표 데모의 실제 서항 배수권역·센서·CCTV·펌프 매핑과 서항 적용 여부

- 각 유형군의 실제 데이터·모델 준비도와 대상 기관 재난분류 매핑
- 사건 후보를 자동 생성·연결할 세부 임계치·시간창·공간 기준
- IA-05·대응 모의훈련의 실제 권한과 담당 조직. 이번 데모에서는 정하지 않고 추후 제품 개발 시 정의

확인되지 않은 값을 실제 사실처럼 문서에 적지 않는다. 확인되면 이 README의 상태와 02·03·IA를 갱신한다.
