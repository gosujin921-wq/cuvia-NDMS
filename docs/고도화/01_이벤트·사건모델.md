# CUVIA Phase 2 이벤트·사건 모델

> 상태: 기준안 - 재검수 잔여항목 반영 완료·외부 명세 확인 필요
>
> 기준일: 2026-09-10
>
> 목적: CUVIA가 무엇을 이벤트로 받아들이고, 여러 이벤트를 어떻게 하나의 재난 사건으로 연결하며,
> 그 사건을 디지털트윈·판단·대응·기록에 어떻게 사용하는지 정의한다.

## 1. 결론부터

CUVIA는 센서 알람을 지도에 모아 보여주는 시스템에 머물지 않는다.

> **서로 다른 출처에서 발생한 시간·공간 기반 사실을 공통 이벤트로 정규화하고, 관련 이벤트를 담당자가
> 판단할 하나의 재난 사건으로 연결한 뒤, 현재 상태와 미래 영향을 함께 구성하는 사건 중심 의사결정
> 지원 시스템으로 설계한다.**

분류와 수량은 백업 문서에서 승계하지 않고 사업·자사·타사 원본과 공식 기준을 다시 대조해 정의한다.

이 구조에서 가장 중요한 구분은 다음과 같다.

```text
원천 데이터        장비·기관·사람·모델이 제공한 원본
    ↓
정규화 이벤트      언제, 어디서, 무엇이 어떻게 변했는지 표현한 사실
    ↓ 파생 규칙·AI·모델 분석과 감시 우선순위
사건 후보           관련 이벤트를 시스템이 묶어 제안한 업무 단위(Incident의 `후보` 상태)
    ↓ 담당자 확인
재난 사건           판단·예측·대응·기록을 함께 관리하는 운영 단위
    ↓
예측·권고·결정·실행·결과
```

분석은 사건 확인 뒤에만 실행되는 고정 단계가 아니다. 예측·장면분석·위험평가는 감시 또는 후보 단계에서도
생길 수 있으며, 사건에 연결된 뒤에는 사용한 원천과 사건 ID를 함께 남긴다.

센서 한 건, 특보 한 건, VLM 문장 하나를 곧바로 재난 사건이라고 부르지 않는다.
사건 후보는 별도 데이터 객체를 하나 더 만드는 개념이 아니라, 근거 검토 전 `Incident`의 처리상태다.

## 2. 원본과 추가 조사에서 확인한 설계 근거

### 2.1 창원 도시침수 실증

`24년도시침수 완료보고_20250325_v1.0.pdf`에서 확인되는 사실은 다음과 같다.

- 창원 재난상황시스템은 강우·하천수위·우수받이를 기축 API와 신축 Socket, 도로·관로수위와
  유량·유속을 신축 Socket 연계 대상으로 제시하고 CCTV 실시간 스트리밍을 제시한다(p.18). 이는
  연계 설계이며 현재 각 데이터가 모두 제공된다는 뜻은 아니다.
- 우수저류조, 배수펌프장, 지하차도·하천진입 차단시설은 이벤트 방식으로 연계 대상으로 제시된다
  (p.18).
- 기상 관측·예측, 레이더, 하천수위·유량과 도시침수예측은 서로 다른 출처·갱신 주기로 연계 대상으로
  제시된다(p.18-19). 조위는 p.18 창원 연계 항목이 아니라 침수 예측모형의 관측·예측 입력으로 확인된다
  (p.39).
- 예측모형은 지형·배수구역·관로·펌프 제원·강우·수위·조위 등 여러 입력을 사용하고, 침수심과 범위를
  결과로 만든다(p.39).
- 실증에서는 반복 알람, 센서와 CCTV의 공간 분리, 지역 특화 모형, 예측과 실측의 신뢰성 검증이
  과제로 남았다(p.60-62).
- 원문에는 관로와 도로수위 계측자료를 활용해 30~40분의 예보 선행시간을 확보했다고 기재돼 있다
  (p.62, 한강홍수통제소 보고서 발췌).

30~40분은 해당 분석 결과이며 모든 지역의 고정 성능으로 일반화하지 않는 것이 Phase 2의 설계 판단이다.

따라서 CUVIA는 단순 임계치 알람 수를 사건 수로 계산하면 안 된다. 출처·시각·위치·품질·갱신 주기가
다른 데이터를 보존하면서 하나의 사건 근거로 연결해야 한다.

### 2.2 자사 자료

`창원시_지능형재난안전솔루션(쿠비아)_REV 1.0.pdf`는 사건 수신부터 모니터링, 전파, 조치, 종료·보고까지
One-Stop 흐름을 제안하고(p.12), AI 판단(p.14), E-SOP(p.16-18), 침수 영향 예측(p.20),
디지털트윈 기반 정보 표출(p.22)을 제품 방향으로 제시한다.

`지능형재난안전솔루션(쿠비아)_요약설명자료_v0.2_20260908.pptx`는 사전 감시부터 감지, 종합 판단,
영향 예측, 전파·조치, 현장 보고, 자동 기록, 학습·대비까지 8단계 흐름을 제시한다(슬라이드 2).

이 내용은 **목표 비전**이다. 현재 구현 또는 실증이 8단계를 자동 수행한다는 증거로 사용하지 않는다.

### 2.3 타사·협력사 자료

- 지오멕스소프트 자료는 다종 센서·CCTV·기관 데이터 수집, 임계치, 유형별 위험도, 투망 모니터링,
  SOP 호출과 대응 이력 저장을 이미 제안한다.
- RINO는 상황접수→분석→전파→대응→종료를 이벤트 분석, 상황전파, 워크플로우 모듈로 분리한다.
- TwinRIS-ON은 계측·CCTV·기상 모니터링, 3D 시각화, 계측 데이터 포워딩과 상위기관 연계를 강점으로
  제시한다.

따라서 CUVIA의 차별점을 “타사는 수집·임계치만 한다”로 두기 어렵다. 차별점은 **여러 근거가 왜 하나의
사건이 되었는지 설명하고, 같은 사건에서 예측·대안·승인·실행·결과를 끊김 없이 추적하는 구조**로 잡는다.

### 2.4 공식 기준에서 가져올 원칙

아래 표준을 특정 구현 기술로 확정하지 않는다. 데이터 필드와 관계를 빠뜨리지 않기 위한 설계 기준으로
사용한다.

| 공식 기준 | 가져올 원칙 | CUVIA 적용 |
|---|---|---|
| [CloudEvents](https://github.com/cloudevents/spec/blob/main/cloudevents/spec.md) | 이벤트의 `id`, `source`, `type`, `time`, `subject`와 중복 식별 | 출처가 달라도 공통 이벤트 봉투로 수집 |
| [OGC SensorThings API](https://www.ogc.org/standards/sensorthings/) | Thing·Sensor·Datastream·Observation·Location 분리 | 장비, 측정 방식, 관측값과 위치를 분리 |
| [OGC API EDR](https://docs.ogc.org/is/19-086r6/19-086r6.html) | 위치·영역·경로·시간으로 환경 데이터를 조회 | 기상·수문·예측 자료의 시공간 요청 기준 |
| [ETSI NGSI-LD](https://cim.etsi.org/NGSI-LD/official/introduction.html) | 실세계 객체의 속성·관계·시간 변화를 디지털트윈으로 관리 | 시설·구역·사건의 현재 상태와 관계 구성 |
| [OASIS CAP 1.2](https://www.oasis-open.org/standard/cap/) | 긴급도·심각도·확실성·대상지역·갱신·취소 분리 | 외부 특보와 대외 경보 메시지의 의미 보존 |
| [ISO 22320:2018](https://www.iso.org/standard/67851.html) | 역할·책임·업무·자원·기관 간 공동 대응 | 시스템 권고와 담당자·기관의 결정 경계 |
| [WMO Early Warnings for All](https://wmo.int/all-activities/build-resilience/early-warnings-all) | 위험지식→관측·예측→전파→대응의 종단 흐름 | 화면 기능이 아니라 전체 업무 가치사슬 검증 |
| [NIST AI RMF 1.0](https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-ai-rmf-10) | 신뢰성·설명가능성·책임성과 인간 역할 명시 | VLM·AI 권고와 사람 확인·승인 분리 |

## 3. 먼저 분리해야 할 네 가지 분류

기존 문서와 화면에서 `이벤트 유형`, `재난유형`, `처리상태`가 섞이면 같은 단어가 서로 다른 질문에
답하게 된다. Phase 2에서는 아래 네 축을 독립적으로 관리한다.

| 축 | 답하는 질문 | 예시 |
|---|---|---|
| 이벤트 유형 | 무엇이 발생하거나 변했는가? | 수위 관측, 특보 발표, 펌프 상태 변경, 현장 보고 |
| 사건 위험유형 | 어떤 위험을 담당 업무로 관리하는가? | 도시침수, 하천범람, 산불, 기반시설 장애 |
| 트윈 유형군 | 어떤 상태·전파·시간·공간 계산 문법을 쓰는가? | A 도시 배수·침수, B 하천 흐름·범람 |
| 처리상태 | 담당 업무가 어디까지 진행됐는가? | 후보, 확인중, 확인됨, 대응중, 통제, 종료, 오탐, 병합됨 |

하나의 `수위 관측` 이벤트는 내수침수·하천범람·폭풍해일 사건에 각각 근거가 될 수 있다. 반대로 하나의
내수침수 사건에는 강우, 관로수위, 도로수위, 펌프 상태, 조위, CCTV와 현장 보고가 함께 연결될 수 있다.
태풍·집중호우는 기본적으로 사건의 기상 조건이며, 독립 담당·조치·처리상태가 필요한 경우에만 사건
위험유형으로 등록한다. 사건 위험유형과 A~G 트윈 유형군의 기관별 매핑은 대상 기관 분류를 확인한 뒤 정한다.

## 4. CUVIA가 받아들이는 입력

### 4.1 입력원 분류

| 입력원 | 대표 데이터 | 이벤트로 만드는 변화 | 주요 활용 |
|---|---|---|---|
| 계측 센서 | 강우, 하천·관로·도로·저수지 수위, 유량·유속, 변위, 온습도 | 새 관측, 임계치 통과, 급상승·급변, 결측·장애 | 현재 상태, 추세, 사건 후보, 트윈 초기조건 |
| CCTV·VLM | 영상, 스틸컷, 객체·장면 분석 | 침수 시작, 연기·불꽃, 도로 통행상태, 분석 실패 | 교차확인, 공간 범위 보정, 현장 상태 근거 |
| 기상·해양 | 관측·예측 강우, 레이더, 특보, 풍향·풍속, 기온, 조위 | 예측 갱신, 특보 발표·변경·해제 | 사전 감시, 원인 조건, 트윈 경계조건 |
| 시설·제어 | 펌프, 수문, 저류시설(저류조), 차단기, 방송·전광판 | 상태·가용성 변경, 제어 요청, 성공·실패·미응답 | 배수·통제 조건, 대안 비교, 실행 결과 |
| 기관 시스템 | NDMS 사건 메시지(수신 확인 필요), 소방 출동, 도로통제, 상급기관 지시 | 신규·갱신·취소·종료 메시지 | 공식 상황 연결, 중복 사건 확인, 기관 공조 |
| 현장·사용자 | 전화, 모바일 보고, 사진, 확인·오탐·조치 입력 | 현장 확인, 피해 보고, 조치 결과 | AI·센서 검증, 사건 확정, 실제 결과 기록 |
| 예측·분석 모델 | 침수, 산불확산, 열·대기, 위험도 계산 | 분석 실행, 새 예측판 생성, 유효기간 종료 | 기준 전망, 대안 전망, 영향과 불확실성 |

### 4.2 이벤트가 아닌 입력

다음은 그 자체로 이벤트가 아니라 사건과 분석에 맥락을 제공하는 기준 데이터다.

- DEM, 건물, 도로, 하천, 관로와 배수구역
- 침수흔적도, 도시침수지도, 산사태·산불 발생이력
- 병원, 대피소, 학교, 취약계층과 중요시설
- 펌프·저류시설(저류조) 용량, 수문 제원, 도로 통제 구간, SOP와 연락망
- 행정구역, 위험지구와 담당기관 경계

기준 데이터의 버전이 바뀌면 `REFERENCE_DATA_UPDATED` 이벤트를 남길 수 있지만, 매 화면에서 정적 레이어를
실시간 사건 이벤트처럼 세지 않는다.

완료보고서 p.18의 NDMS 항목은 계측기·차량제어 정보를 표준플랫폼에서 재난안전포털로 보내는 방향이다.
NDMS 사건을 CUVIA가 수신하는 구조는 현재 원본에서 확인되지 않았으므로 P1 확인 전까지 제안 입력으로만
둔다.

## 5. 공통 이벤트 구조

모든 입력을 똑같은 데이터로 만들 필요는 없다. 다만 사건 연결과 추적에 필요한 공통 봉투는 가져야 한다.

| 필드 | 의미 | 필수 |
|---|---|---|
| `eventId` | 정규화 이벤트의 고유 식별자 | 필수 |
| `sourceSystem` | 이벤트를 제공한 시스템·기관 | 필수 |
| `sourceEventId` | 원천 시스템의 식별자 | 가능하면 필수 |
| `eventType` | 관측·특보·상태변경·보고 등 의미 유형 | 필수 |
| `eventClass` | 원천·파생·분석·업무 중 이벤트의 생성 계층 | 필수 |
| `producerRole` | 원천 기관·CUVIA 규칙·모델·담당자 등 이벤트를 생성한 주체의 역할 | 필수 |
| `subjectId` | 센서·CCTV·시설·구역·모델 등 대상 | 필수 |
| `observedAt` | 실제 현상이 발생·관측된 시각 | 필수 |
| `receivedAt` | CUVIA가 수신한 시각 | 필수 |
| `validFrom/To` | 특보·예측·상태의 유효시간 | 조건부 |
| `location/geometry` | 지점·선·구역·전역의 공간 범위 | 원천·분석 이벤트 필수 |
| `value/unit` | 관측값과 단위 | 조건부 |
| `quality` | 정상·지연·결측·의심·보정 등 데이터 품질 | 원천·파생·분석 이벤트 필수 |
| `sourceReadiness` | 실연계·연계 가능·협의 필요·내부 생성 등 출처·연계 준비도 | 시연·검증 이벤트 필수 |
| `dataOrigin` | 실제 API·원본 파일·승인 표본·합성 데이터·사용자 입력 | 시연·검증 이벤트 필수 |
| `calculationActor` | CUVIA 계산·외부 모델 수신·해당 없음 | 예측·분석 이벤트 필수, 그 외 해당 없음 |
| `payload` | 원본 또는 원본 참조 | 필수 |
| `schemaVersion` | 해석할 데이터 계약 버전 | 필수 |
| `correlationKeys` | 장비·배수구역·하천·도로 등 사건 연결 키 | 조건부 |
| `supersedes/cancels` | 정정·갱신·취소 대상 | 조건부 |
| `incidentId` | 연결된 CUVIA 사건 식별자 | 사건에 연결된 분석·업무 이벤트 필수 |
| `derivedFrom[]` | 파생값·분석·권고를 만든 입력 이벤트 식별자 | 파생·분석 이벤트 필수 |
| `references[]` | 결정·실행이 참조한 근거·권고·결정·선행 이벤트 식별자 | 업무 이벤트 조건부 |
| `actor` | 담당자·시스템·기관 등 상태변경과 결정의 수행 주체 | 업무 이벤트 필수 |
| `ingestionMode` | 실시간·재생·모의·수동 등 시연·수집 방식 | 필수 |

원본은 변경하지 않고 보존한다. 단위 변환, 위치 매핑, 품질 판정과 파생값은 원본과 별도 필드에 기록한다.
사건에 종속된 결정·실행 이벤트는 자체 위치 대신 `incidentId`를 통해 사건 공간을 참조할 수 있다.

### 5.1 이벤트 생성 계층

| 계층 | 의미 | 대표 유형 | 필드 적용 원칙 |
|---|---|---|---|
| 원천 | 외부 시스템·장비·사람이 제공한 사실 | 관측, 특보, 시설상태, 현장보고, 외부 사건 | 위치·품질·원본 참조 필수 |
| 파생 | 원천값을 규칙으로 변환한 결과 | 임계치 통과, 변화율, 품질상태 | `derivedFrom[]`과 규칙·버전 필수 |
| 분석 | 모델·AI가 만든 해석과 전망 | 장면분석, 예측, 위험평가, 권고 | `derivedFrom[]`, 모델·버전·불확실성 필수 |
| 업무 | 사건 처리·결정·실행 과정의 기록 | 사건 생성·상태·관계, 검토 요청, 결정, 조치, 전파·결과 | `incidentId`, `actor`, 사유·결과와 해당 시 `references[]` 필수 |

결과·품질 유형도 생성 주체에 따라 계층이 달라질 수 있다. 외부 시스템이 보낸 품질 상태는 원천,
CUVIA가 미수신 시간을 판정한 `DATA_QUALITY_CHANGED`는 파생이다. `ASSESSMENT_UPDATED`,
`RECOMMENDATION_UPDATED`와 `MODEL_RUN_COMPLETED`는 분석, 모델 실행 요청·실패, 제어·전파 결과와
`OUTCOME_RECORDED`는 업무 계층으로 기록한다.
유형명만으로 계층을 추정하지 않고 `eventClass`와 생성 주체를 함께 기록한다.

`MODEL_RUN_COMPLETED/FAILED`는 한 번의 모델 실행 생애주기를 기록한다. 그 실행 결과가 활성 예측판을
새로 만들거나 교체하면 별도의 `FORECAST_UPDATED`를 생성하고 모델 실행 이벤트를 참조한다. 외부 예측
수신은 원천, CUVIA가 계산·해석한 예측판 갱신은 분석 계층이다.

### 5.2 시간은 하나가 아니다

- `observedAt`: 실제 관측·발생 시각
- `receivedAt`: 플랫폼 수신 시각
- `validFrom/To`: 특보와 예측이 유효한 시작·종료 시각
- `forecastBaseTime`: 예측을 생성한 기준 시각
- `recordedAt`: 담당자가 확인·입력한 시각

화면에서 최신 데이터처럼 보여도 `observedAt`과 `receivedAt`의 차이가 크면 지연 상태로 표시한다.
`forecastBaseTime`은 Forecast·모델 이벤트의 payload, `recordedAt`은 담당자 업무 이벤트의 payload에
두며 공통 이벤트 봉투의 필수 필드로 중복시키지 않는다.

### 5.3 중복·정정·취소

- 원천이 식별자를 제공하면 `sourceSystem + sourceEventId`로 같은 이벤트의 재전송을 판별한다.
- 식별자가 없으면 대상·유형·관측시각·값의 지문을 만들어 중복 후보를 찾는다.
- 정정과 갱신은 기존 이벤트를 덮어쓰지 않고 `supersedes` 관계로 연결한다.
- 특보 해제와 메시지 취소는 원래 발표가 없어진 것이 아니라 상태가 바뀐 새 이벤트로 남긴다.
- 반복 임계치 알람은 모두 보존하되 사건 수와 별도로 집계한다.

| `DISSEMINATION_REQUESTED` | 승인된 전파 요청 기록 | 대상 지역에 재난문자 발송 요청 |
| `DISSEMINATION_RESULT_RECORDED` | 매체별 성공·실패·미응답과 대체조치 기록 | 마을방송 실패 후 유선 연락 |
| `OUTCOME_RECORDED` | 원천 관측·현장·조치 결과를 종합한 사건 결과와 검증 기록 | 실제 도로수위와 예측 침수심 비교 |
| `REPORT_GENERATED` | 사건 기록으로 보고서 초안·확정본 생성 | 상황보고서 초안 생성 |

`THRESHOLD_CROSSED`와 `RATE_CHANGED`는 원천 이벤트가 아니라 관측을 규칙으로 변환한 파생 이벤트다.
위험평가와 권고는 모델·규칙의 해석이 포함된 분석 이벤트다. 사건 상태·관계, 결정과 실행 이벤트는
원천 관측이 아니라 CUVIA 안에서 발생한 업무
기록이다. 어떤 원천·규칙·담당자 행위에서 만들어졌는지 추적해야 한다.

## 7. 이벤트를 사건으로 연결하는 규칙

### 7.1 사건 후보 생성

사전 감시는 아직 Incident가 아니다. 예측강우·특보·취약성만으로는 `감시 우선구역·카메라·시설`을
선정하고, 위험이 해소되면 별도 사건 상태 전환 없이 감시 우선순위에서 내린다.

다음 중 하나가 발생하면 Incident를 `후보` 상태로 만들 수 있다.

- 외부 기관 사건이 새로 접수되거나, 공식 특보에 대해 별도 담당·조치·처리상태가 필요한 대응 업무가 시작됨
- 핵심 센서가 심각 임계치를 통과함
- 여러 센서의 변화가 동일 구역과 시간창에서 함께 나타남
- VLM 또는 현장 보고가 명시적인 위험 장면을 확인함
- 예측 결과가 사전에 정한 사건 후보 영향 기준을 초과함
- 담당자가 수동으로 사건을 등록함

예측판이 갱신됐다는 사실 자체로는 후보를 만들지 않는다. 사전에 정한 영향 기준을 넘은 예측 결과만 위 조건에
따라 후보 근거가 된다. 대표 데모에서는 예측강우 상향으로 D0 감시 우선대상을 정하고, 관로수위 급상승과
침수예측판(E8)이 함께 나타나는 D1에서 사건 후보를 만든다. 후보 생성은 사건 확정이 아니다.

### 7.2 기존 사건에 연결

새 이벤트를 기존 사건에 연결할 때 다음 조건을 함께 본다.

1. **공간:** 같은 지점·시설·배수구역·하천·영향구역에 속하는가?
2. **시간:** 사건의 활성 시간과 이벤트 유효시간이 겹치는가?
3. **의미:** 해당 재난유형에서 원인·징후·영향·조치로 설명 가능한가?
4. **관계:** 기존 사건의 근거인지, 외부참조인지, 별도 원인·악화·파생·동시발생 사건을 제안하는가?
5. **품질·방식:** 결측·지연·의심 상태와 재생·모의 여부를 고려했는가?

단순히 위치와 시간이 가깝다는 이유만으로 자동 병합하지 않는다. 태풍·집중호우는 기본적으로 기상·특보
이벤트와 사건의 원인 조건으로 연결한다. 시 전체 대응처럼 별도 담당 조직·조치·처리상태가 필요할 때만
상위 Incident로 만들고 내수침수 등 영향 사건과 원인·파생 관계로 연결한다.

### 7.3 자동화와 사람 확인

| 시스템이 할 수 있는 일 | 담당자가 확정할 일 |
|---|---|
| 중복 제거와 후보 이벤트 연결 | 사건 확인·병합·분리·오탐 처리 |
| 임계치·변화율·위험도 계산 | 업무상 재난단계와 대응 수준 결정 |
| VLM 장면 설명과 신뢰도 제시 | 실제 영상 확인과 현장 판단 |
| 기준·대안 예측 실행 | 사용할 조건과 대응안 선택 |
| SOP·전파문·보고서 초안 | 승인, 수정, 실행과 최종 확정 |

AI 결과는 원천 사실이 아니라 `분석 결과`로 표시하고 모델·버전·생성시각·입력 근거를 남긴다.

### 7.4 사건 처리상태와 전환

| 현재 상태 | 전환 조건 | 다음 상태 | 확정 주체 |
|---|---|---|---|
| 후보 | 담당자가 후보 검토를 시작하거나 담당 업무로 인수 | 확인중 | 담당자 |
| 후보 | 명백한 시험·중복·오경보로 판정 | 오탐 | 담당자 |
| 후보·확인중·확인됨 | 다른 사건과 같은 원인·영향·업무 단위임을 확인 | 병합됨 | 담당자 |
| 확인중 | 영상·현장·기관 정보로 실제 대응할 사건임을 확인 | 확인됨 | 담당자 |
| 확인중 | 오경보·중복·시험 데이터로 판정 | 오탐 | 담당자 |
| 확인됨 | 대응안이 승인되고 하나 이상의 조치가 시작됨 | 대응중 | 담당자·승인자 |
| 대응중 | 급격한 확대가 멈추고 조치가 유지되는 감시 상태로 전환 | 통제 | 담당자 |
| 통제 | 종료 조건을 충족하고 잔여 조치·확인사항이 정리됨 | 종료 | 담당자 |
| 종료 | 같은 원인 사건이 계속되며 위험 징후가 다시 발생 | 확인중 또는 대응중 | 담당자 |

`통제`는 도로 통제 같은 개별 조치가 아니라, 사건의 급격한 확대가 멈췄지만 종료 전 감시와 잔여 대응이
필요한 상태를 뜻한다. 특보 해제나 센서값 정상화 하나만으로 사건을 자동 종료하지 않는다.

자동·수동 등록 모두 초기 상태는 `후보`로 둔다. 담당자가 등록과 동시에 검토를 인수하더라도
`INCIDENT_CREATED(후보)`와 `INCIDENT_STATUS_CHANGED(확인중)`를 구분해 남긴다.

### 7.5 병합·분리·종료·재개 규칙

- **병합:** 같은 위험현상, 공간 영향권, 활성 시간과 담당 업무를 공유할 때만 병합한다. 흡수된 사건은
  `병합됨`으로 남기고 기준 사건 ID와 병합 사유·담당자·시각을 기록한다. 이때 기준 사건과의
  `merged_into` 관계를 남기는 `INCIDENT_RELATION_CHANGED`와 흡수 사건을 `병합됨`으로 바꾸는
  `INCIDENT_STATUS_CHANGED`를 같은 처리 단위에서 모두 기록한다.
- **분리:** 하나의 후보 안에서 원인, 영향권, 담당 조직 또는 대응 상태가 독립적으로 움직이면 별도 사건을
  만들고 원인·악화·파생·동시발생 관계를 연결한다.
- **종료:** 위험 관측의 하강·해제, 영향 확산 중단, 필수 조치 결과 확인과 담당자 판단을 함께 충족해야 한다.
  미응답·실패 조치와 미확인 현장 보고가 있으면 종료 사유에 잔여사항을 남긴다.
- **재개:** 같은 원인과 영향권이 이어지는 동안 다시 위험해지면 기존 사건을 재개하고 상태변경 이벤트를
  남긴다. 원인·시간·공간이 새로 분리되면 새 사건으로 생성한다.
- **오탐:** `후보` 또는 `확인중`에서 오탐 처리하며 원천 이벤트와 분석 결과는 삭제하지 않는다. 오탐 사유와 판정
  근거를 남겨 규칙·모델 검토에 사용한다.

## 8. 재난 사건 구조

```text
Incident
├── identity             사건 ID·사건 위험유형·트윈 유형군·제목
├── scope                지점·시설·구역·회랑·전역
├── workflowStatus       후보·확인중·확인됨·대응중·통제·종료·오탐·병합됨
├── ownership            담당 조직·담당자·인계 상태
├── scenarioContext      사건 기준시각·scenarioMode와 이벤트별 dataOrigin·ingestionMode
├── hazardAssessment     4축 판단·위험/완화 요인·반대 근거·불확실성·누락정보
├── evidenceEvents[]     센서·영상·기상·시설·특보·현장·품질·파생·분석 이벤트 참조와 연결 이유·가정 주석
├── externalRecords[]    외부 특보·기관 사건의 원본 식별자와 변경 이력
├── relatedIncidents[]   원인·악화·파생·동시발생·외부참조·병합 관계
├── reviewRequests[]     확인 대상·요청 사유·상태·담당자
├── modelRuns[]          실행 요청·조건·상태(미지원·미실행/실행중/완료/실패)·원인과 생성 예측판
├── forecasts[]          예측판 ID·모델·버전·기준/생성/유효시각·조건·시간별 공간 결과·불확실성·가용상태
├── affectedAreas[]      영향공간 ID·현재/예상 구분·시간·대상
├── recommendations[]    시스템 권고·제안 대응수준·근거·반대근거·제안/변경/철회 상태
├── decisions[]          검토중·선택·승인·기각·취소, 선택 대응수준·담당자·시각·사유
├── actions[]            SOP·전파·시설 요청, 담당·상태·선행/대체 Action
├── outcomes[]           사건 결과·예측/대응 검증과 참조한 관측·현장·조치
└── reports[]            보고서 초안·확정본·버전과 생성 근거
```

관계 유형은 다음 의미로 제한한다.

| 관계 | 의미 |
|---|---|
| 원인 | 한 사건이 다른 사건을 발생시킴 |
| 악화 | 별도 사건이 대상 사건의 조건을 불리하게 만듦 |
| 파생 | 대상 사건의 영향으로 새 운영 사건이 발생함 |
| 동시발생 | 시간·공간은 겹치지만 인과를 확정하지 않음 |
| 외부참조 | 외부 기관 기록과 내부 사건을 추적 가능하게 연결 |
| 병합 | 중복 사건이 기준 사건에 흡수됨 |

외부 기관 사건은 `externalRecords[]`에 원본 ID·상태·변경 이력을 우선 보존한다. 외부 기록 수신만으로
CUVIA Incident를 자동 생성하거나 병합하지 않는다. 시간·공간·위험현상이 맞으면 관계 후보를 제안하고,
담당자 확인 뒤에만 내부 Incident를 만들거나 `외부참조` 관계를 확정한다.

시설 상태변경은 항상 `evidenceEvents[]`에 악화·완화 조건으로 연결한다. 시설 장애가 별도 담당 조직,
독립된 조치와 처리상태를 가져야 할 때만 기반시설 장애 Incident를 만들고 원인 사건과 `악화` 또는 `파생`
관계로 연결한다.

### 8.1 섞지 않을 상태

| 상태 | 질문 |
|---|---|
| 외부 특보 | 기관이 무엇을 발표했는가? |
| 관측 위험단계 | 센서와 규칙이 어느 기준을 넘었는가? |
| 사건 처리상태 | 담당 업무가 어디까지 진행됐는가? |
| 심각도 | 예상 피해가 얼마나 큰가? |
| 긴급도 | 얼마나 빨리 대응해야 하는가? |
| 확실성 | 관측·예측을 얼마나 신뢰할 수 있는가? |
| 도시 대응단계 | 시 전체 운영 수준은 무엇인가? |
| 실행 결과 | 조치가 대기·진행중·성공·실패·미응답·확인대기·대체됨·취소 중 어디에 있는가? |

특보가 발표됐다고 모든 센서를 경계로 바꾸거나, 위험도가 높다고 도시 대응단계를 자동 격상하지 않는다.

도시 대응단계는 개별 Incident의 `workflowStatus`가 아니라 별도 `CityOperationalState`로 관리한다. 변경
시 `CITY_STAGE_CHANGED` 업무 이벤트를 남기고, 변경을 승인한 Decision과 해당 시점의 관련 사건을
`references[]`와 `relatedIncidentIds[]`로 연결한다. Incident에는 판단 당시 도시 대응단계의 참조만 보존한다.

### 8.2 결정과 실행 상태

- `pendingDecisionId`는 `decisions[]` 중 `검토중` 상태인 결정안을 가리킨다.
- 결정 상태는 `검토중·선택·승인·기각·취소`로 통일한다. 결정안 생성은 `검토중`, 담당자의 안 선택은
  `선택`, 최종 권한자의 확정은 `승인`으로 기록하며 `추가 확인`은 검토 요청을 유지하는 결정 사유다.
- Action의 처리상태는 `대기·진행중·성공·실패·미응답·확인대기·대체됨·취소`로 통일한다.
- `FIELD_REPORT_RECORDED`는 현장 담당자가 보낸 원천 보고, `ACTION_STATUS_CHANGED`는 배정된 Action의
  상태 변화, `OUTCOME_RECORDED`는 관측·보고·조치 결과를 종합한 사건 단위 검증이다.
- 대체 Action은 `replacesActionId`로 실패·미응답 Action을 참조하며 기존 Action 기록을 덮어쓰지 않는다.
- `ACTION_*`은 현장 확인·도로 통제·시설 점검과 운영 요청처럼 사람이 수행하는 업무에 사용한다.
- `CONTROL_*`은 장비에 실제 원격제어 명령을 보내는 경우에만 사용하며 Phase 2 대표 데모에서는 쓰지
  않는다.
- `DISSEMINATION_*`은 알림톡·방송·전광판·기관 통보 등 메시지 전파 요청과 채널별 결과에 사용한다.
  전파문 본문은 §2.4의 CAP 1.2 필드(식별자, 심각도·긴급도·확실성, 대상지역, 갱신·취소) 구조를 따른다.

모델·예측 상태는 실행 여부와 결과 가용성을 섞지 않는다. 제품 범위 밖이거나 요청하지 않은 경우는
`미지원·미실행`, 필요한 입력·기능이 없어 대안을 만들 수 없으면 Forecast 가용상태를 `대안 계산 불가`,
실제로 시작한 실행이 오류로 끝난 경우만 ModelRun을 `실패`로 기록한다. 권고와 결정의 대응수준 값은
실제 기관 SOP 확인 전 `감시 강화·현장 확인·선제 통제 검토·통제·종료 검토` 같은 데모 역할명으로 두고,
공식 대응단계처럼 표현하지 않는다.

### 8.3 공간 범위

| 범위 | 예시 | 표현 원칙 |
|---|---|---|
| 지점 | 수위계, CCTV, 맨홀 | 실제 좌표와 장비 상태 |
| 시설 | 펌프장, 지하차도, 저류시설(저류조) | 시설 경계와 구성 장비 |
| 회랑 | 하천, 도로, 해안선 | 선형 구간과 상·하류 관계 |
| 구역 | 배수구역, 위험지구, 행정동 | 실제 영향 폴리곤과 대상 |
| 전역 | 독립 대응이 필요한 태풍, 폭염·지진의 시 단위 영향 | 도시 범위와 지역별 차이 |

지도에 카드를 놓기 위한 `displayAnchor`와 실제 영향 범위 `affectedGeometry`를 분리한다.

## 9. 이벤트의 활용 위치

| 활용 단계 | 사용하는 이벤트 | 생성되는 결과 |
|---|---|---|
| 사전 감시 | 예측 갱신, 특보, 과거 위험·취약성 | 감시 우선구역·카메라·시설 |
| 감지 | 관측, 임계치, 변화율, VLM | 이상 신호와 사건 후보 |
| 종합 판단 | 센서·영상·기상·기관·품질 | 위험도, 근거, 추가 확인 요청 |
| 디지털트윈 | 현재 관측, 예측 기상, 시설 상태, 기준 데이터 | 기준 전망·대안 전망·영향 범위 |
| 대응 결정 | 영향 대상, 긴급도, SOP, 자원 상태 | 권고, 승인안, 전파·조치 대상 |
| 실행 | 현장 확인·도로 통제·시설 점검 Action, 전파 요청, 실제 원격제어 시 제어 요청 | Action·채널·시설별 실행 결과 |
| 기록·검증 | 전체 이벤트, 예측판, 결정, 현장 결과 | 타임라인, 보고서, 예측 대 실제 |

같은 이벤트를 화면마다 복제하지 않는다. 사건에 연결된 공통 근거를 각 화면의 질문에 맞게 다르게
요약한다.

## 10. 대표 데모와 연결한 모델 검증 예시

아래는 `02_대표데모시나리오.md`의 창원 도시침수 대표 사건과 같은 구조를 사용한다. 서항은 실제
배수권역·센서·시설 매핑을 확인하기 전까지 적용 후보로 둔다. 표의 대안 예측과 실제 비교는 관련 데이터를
확보했을 때의 강화 흐름이며, 확보하지 못하면 대표 데모 문서의 핵심 완료 기준만 적용한다.

| 순서 | 들어온 이벤트 | 사건 처리 | 활용 |
|---:|---|---|---|
| 1 | 60분 예측강우 상향 | 사건 생성 전 감시 우선구역 선정 | 취약구역·CCTV 우선 감시 |
| 2 | 관로수위 급상승·복합징후 | `INCIDENT_CREATED`로 사건 후보 생성 | 파생 변화율과 `ASSESSMENT_UPDATED`로 도로침수 가능성 기록 |
| 3 | 조위 상승·펌프 가용성 저하 | 시설·해양 근거를 사건에 연결 | 트윈 기준조건 구성 |
| 4 | VLM이 차로 물고임 추정 | `REVIEW_REQUESTED` 생성 후 담당자가 검토를 인수하고 상태변경을 확정하면 `확인중`으로 전환 | 현장 영상 열기 |
| 5 | 담당자가 영상 또는 현장 보고 확인 | 결정과 상태변경을 남기고 `확인됨`으로 전환 | 예측·대응 작업 시작 |
| 6 | 기준 전망과 펌프 복구 대안 실행 | `MODEL_RUN_REQUESTED`와 완료·실패, 조건별 예측판 저장 | 침수 범위·도달시간 비교 |
| 7 | 도로 통제·전파·펌프 점검 승인 후 첫 조치 시작 | 결정·Action·Dissemination 이벤트를 남기고 `대응중` 전환 | 채널·기관별 결과 추적 |
| 8 | 위험 확대 중단과 잔여 조치 감시 | 담당자 판단으로 `통제` 전환 | 미응답·대체조치 확인 |
| 9 | 실제 도로수위·현장 결과와 종료 판단 | Outcome·보고서 생성과 `종료` 전환 | 예측 오차·대응 결과 기록 |

이 흐름은 “수위 알람이 울려 문자를 보낸다”보다, **왜 사건이 되었고 어떤 조건을 바꾸면 영향이
달라지는지**를 설명한다.

## 11. 데모 데이터의 내부 상태 관리

| 상태축 | 값 | 관리 원칙 |
|---|---|---|
| 연계 준비도 | 실연계·연계 가능·협의 필요·내부 생성 | 실제 연결 여부와 실개발 교체 과제를 내부 계약에 기록 |
| 수집·시연 방식 | 실시간·재생·모의·수동 | fixture·adapter에서 데이터 구성과 사건 기준시각 변환을 관리 |
| 데이터 품질 | 정상·지연·결측·의심·보정 | 제품 판단에 필요한 관측시각·지연·보정 여부와 근거는 화면에 표시 |
| 계산 주체 | CUVIA 계산·외부 모델 수신·해당 없음 | 실제 모델을 사용할 때 모델·버전·기준시각을 화면에 표시하고 교체 대상은 내부 관리 |

한 이벤트는 각 축에서 하나의 값을 가진다. 예를 들어 `연계 가능 + 재생 + 정상 + 외부 모델 수신`처럼
조합할 수 있지만 `연계 또는 재생`처럼 서로 다른 축을 한 상태값으로 합치지 않는다.

`scenarioMode`는 이벤트 상태축이 아니라 사건 전체의 현상·예측 데이터 구성 방식이다. 대표 데모에서는
`정렬된 과거 재생`, `혼합 데모`, `완전 모의` 중 하나를 선택한다. 혼합 데모는 실제 API·원본 재생·승인
표본·시나리오 데이터를 하나의 기준시각에 맞춰 조합하며, 각 이벤트의 `dataOrigin`과 `ingestionMode`를
내부 데이터 계약에 기록한다. 다른 지역·시점의 표본을 사건에 맞게 변환하면 원본 재생이 아니라 `합성 데이터 + 모의`로
기록한다. 담당자 입력은 `ingestionMode=수동`, 시연 중 시스템이 실제 생성한 업무 이벤트는
`ingestionMode=실시간`으로 기록하며 두 경우의 연계 준비도는 `내부 생성`이다.

합성 입력을 실제 계산 엔진에 넣어 산출했다면 계산 주체와 입력·모델·버전을 기록할 수 있다. 지형에 임의
수위나 형상을 적용해 만든 시각화처럼 검증된 예측 계산이 아니라면 `CUVIA 계산`이 아니라
`해당 없음`으로 기록한다. 이 구분과 향후 실제 모델 교체 지점은 fixture·adapter·기획 문서에 남긴다.
기본 제품 UI에는 `가상`, `더미`, `계산 결과 아님` 같은 제작 구분이나 면책 문구를 노출하지 않는다.
다만 관측시각·갱신시각·출처기관·모델·버전·데이터 품질처럼 실제 운영 판단에 필요한 정보는 정상적인
제품 정보로 제공한다.

`비교 개념`은 계산 주체나 수집 방식이 아니라 Phase 2에서 해당 유형을 다루는 문서·표현 역할이다.
계산 결과가 없는 R0 유형은 계산 주체 `해당 없음`과 역할 `비교 개념`을 내부에서 각각 구분한다. 표본 사용 승인은 별도 데이터 사용권한 메타데이터이며
`ingestionMode` 값으로 넣지 않는다.

## 12. 결정 상태

### 12.1 Phase 2 기준안

- 이벤트 유형, 재난유형, 처리상태를 분리한다.
- 원천 이벤트는 보존하고 정규화·파생 이벤트를 별도로 기록한다.
- 사건은 여러 이벤트를 묶는 업무 단위이며 자동 후보와 담당자 확정을 구분한다.
- 디지털트윈 결과도 사건에 연결되는 버전형 분석 결과로 관리한다.
- 특보·위험도·처리상태·도시 대응단계·실행 결과를 서로 독립된 상태로 관리한다.
- 백업 문서의 기존 유형 수와 사건 수는 승계하지 않는다.
- 사건 확인 전 시스템은 데이터 조회·정규화·후보 연결·분석 실행·내부 검토 알림까지만 자동 수행한다.
  외부 전파, 시설 제어와 업무상 대응단계 변경은 담당자 승인 없이 실행하지 않는다.
- 외부 NDMS 사건은 원천 식별자와 변경 이력을 보존한다. CUVIA 사건과 자동 병합하지 않고 관계 후보로
  제시하며, 담당자가 같은 운영 사건으로 확인하더라도 외부 원본과의 추적 관계는 유지한다.
- Phase 2 데모의 시설 기능은 `요청·승인·결과 확인`으로 제한한다. 실제 원격제어는 권한·연계·안전 절차가
  확인된 별도 범위에서만 다룬다.
- VLM은 감시 우선순위와 사건 근거를 만드는 분석 보조로 사용한다. VLM 결과만으로 사건 확정, 대외 전파
  또는 시설 조치를 승인하지 않는다.

### 12.2 외부 확인이 필요한 항목

| 우선순위 | 확인 항목 | 확인 결과가 바꾸는 것 |
|---|---|---|
| P0 | 창원 도시침수 대표 사건의 실제 배수권역·센서·시설 식별자와 공간 매핑 | 사건 연결 키·공간 규칙·서항 적용 여부 |
| P0 | 각 원천의 실제 식별자, 관측시각·수신시각, 갱신·정정·취소 제공 방식 | 공통 이벤트 필드와 중복 제거 방식 |
| P0 | 도시침수 예측판의 모델·버전·기준시각·유효시간·공간 결과 제공 여부 | Forecast 연결과 기준 전망 시연 범위 |
| P1 | NDMS 사건 메시지의 실제 ID·상태·갱신·종료 구조 | 외부 사건 관계 규칙의 상세 매핑 |
| P1 | CCTV 사용 권한, 사건 시점 영상과 VLM 분석 결과 확보 가능 여부 | 영상 교차확인 이벤트의 실데이터·모의 구분 |
| P1 | SOP·담당 조직·승인 절차와 시설 요청 결과 수신 여부 | 결정·Action 이벤트와 데모 역할명 |

세부 임계치, 시간창, 거리와 사건 자동연결 가중치는 위 P0·P1 자료를 확인한 뒤 구성값으로 정한다. 현재
문서의 예시 수치를 운영 기준으로 사용하지 않는다.

## 13. 완료 기준

- 모든 원천 입력이 논리 출처, `dataOrigin`, 대상, 시각, 위치, 품질과 수집·시연 방식을 가진다.
- 사건에 연결된 분석·업무 이벤트가 `incidentId`, 수행 주체, `derivedFrom[]` 또는 `references[]`를 통해
  사용한 근거로 역추적된다.
- 반복 알람 수와 실제 사건 수를 구분할 수 있다.
- 하나의 사건에서 연결된 원천 이벤트를 역추적할 수 있다.
- 시스템 추론과 담당자 확인을 구분할 수 있다.
- 현재 관측, 예측, 권고, 결정, 실행과 결과가 서로 다른 객체로 남는다.
- 정정·취소·실패·대체조치가 기존 기록을 지우지 않고 연결된다.
- 대표 사건 한 건을 수집부터 사후검증까지 표현할 수 있다.
