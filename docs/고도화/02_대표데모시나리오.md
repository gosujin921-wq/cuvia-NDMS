# CUVIA Phase 2 대표 데모 시나리오

> 상태: 기준안 - 재검수 잔여항목 반영 완료·P0 자료 확인 필요
>
> 기준일: 2026-09-10
>
> 기준안: 창원 도시침수 대표 사건 - 서항 적용 후보

## 1. 데모가 증명해야 하는 것

대표 데모는 화면 수나 재난유형 수를 보여주는 영상이 아니다. 한 사건을 통해 다음 질문에 답해야 한다.

> **CUVIA가 서로 다른 이벤트를 왜 하나의 사건으로 묶었고, 앞으로의 영향을 어떻게 비교했으며,
> 담당자가 어떤 근거로 대응을 결정했는가?**

데모가 끝났을 때 다음 다섯 가지가 기억되어야 한다.

1. 여러 시스템의 이벤트가 하나의 사건 근거로 연결된다.
2. AI와 예측의 결론만이 아니라 사용한 데이터와 가정이 보인다.
3. 디지털트윈은 3D 효과가 아니라 현재 조건과 대안을 비교하는 판단 도구다.
4. 시스템 권고와 담당자 확인·승인이 분리된다.
5. 실행 성공·실패와 실제 결과가 사건 기록으로 남는다.

## 2. 후보 사건 비교

원본 자료에서 확인 가능한 데이터·모델과 데모에서 보여줄 판단 흐름을 기준으로 후보를 비교했다. 기존
백업 문서의 선택은 근거로 사용하지 않았다. 근거 없는 높음·중간 점수 대신 확인된 근거, 보여줄 차이와
현재 제한을 직접 적는다.

| 후보 | 확인된 근거 | 보여줄 트윈·대응 차이 | 현재 제한과 판정 |
|---|---|---|---|
| 창원 도시침수 - 서항 적용 후보 | 창원 시 전체 연계·모형·실증과 서항 배수펌프장 CCTV 위치 | 복합 이벤트 사건화, 배수권역 침수 전망, 통제·배수·전파 연결 | 동일 배수권역의 센서·예측판 미확인, **우선 검증안** |
| 창원 일반 내수침수 | 창원 도시침수 실증 데이터와 모형 구조 | 서항과 같은 A 유형의 일반화 | 위치 앵커가 없어 대표 데모 우선순위 낮음 |
| 해안 폭풍해일 | 조위가 침수모형 입력으로 사용됨 | 해안선·월류구간·만조 시간축과 해안통제 | 창원 조위 실연계·전용 모형 미확인, 비교 설계 후보 |
| 하천범람 | 하천수위·유량·강우 연계 항목 | 상류→하류 도달시간과 하천 구간 통제 | 대상 하천·예측모델·SOP 미확인, 확장 설계 |
| 산불 확산 | 타사 사례의 확산 표현 | 방향성 있는 화선·플룸과 대피방향 | 자사 데이터·모형 근거 부족, 정적 개념 후보 |
| 폭염 | 활용 가능한 기상·취약성 데이터 범주 | 면 단위 누적 노출과 보호자원 | 자사 실증·공식 지표·권한 근거 부족, 장기 후보 |

창원 도시침수 기준안은 단순한 `수위 상승`이나 `폭풍해일` 사건으로 정의하지 않는다. 집중호우, 높은 조위,
관로수위 상승과 배수시설 제약이 같은 배수권역에서 결합해 도로침수 위험을 만드는 **복합침수 사건**으로
정의한다. 서항은 이를 적용할 우선 후보지만 P0 공간·장비 매핑 전에는 확정 대상지역으로 표현하지 않는다.

서항의 실제 준비도는 §12 P0·P1 표에서 별도로 판단한다. 일반 내수침수보다 서항을 먼저 검증하는 이유는
데이터가 더 완성돼서가 아니라 CCTV·배수펌프장이라는 구체적인 현장 앵커가 확인됐기 때문이다.

## 3. 원본 근거와 한계

### 3.1 원본에서 확인된 것

`24년도시침수 완료보고_20250325_v1.0.pdf`에서 다음을 확인했다.

- 창원은 강우·하천수위·우수받이를 기축 API와 신축 Socket, 도로·관로수위와 유량·유속을 신축 Socket
  연계 대상으로 두고 CCTV 실시간 스트리밍을 제시한다(p.18). 현재 전체 데이터가 연결됐다는 뜻은 아니다.
- 우수저류조, 배수펌프장, 지하차도와 하천진입 차단시설 상태를 이벤트로 연계한다(p.18).
- 기상 관측·예측과 도시침수예측의 연계 경로는 확인된다(p.19). 관측·예측 조위는 모형 입력으로
  확인되지만(p.39), p.18의 바다누리 조위 연계 행은 포항 표에 있어 창원 실연계 근거로 사용하지 않는다.
- 도시침수 모형은 지형·배수구역·관로·펌프 제원·가동률·강우·수위·조위를 입력으로 사용한다(p.39).
- 2023~2024년 창원 구축 물량은 도로수위 20, 관로수위 20, 하천수위 4, 하천유속 2, 강우 4로 총
  50개 계측 지점이며 CCTV 관제는 32개로 제시된다(p.26). 이는 시 전체 구축 수량이지 서항 배수권역
  매핑은 아니다.
- 해운동 서항의 CCTV 1개소는 제2배수펌프장 옥상 보안등, 인접한 다른 CCTV 1개소는 배수펌프장
  배수관리용 폴에 설치된 것으로 기재돼 있다(p.29).
- 2024년 9월 20일 창원 실증에서는 우수받이 102회, 도로 83회, 관로 290회, 하천 21회와 침수예측
  30회의 알람이 기록됐다(p.60). 보고서만으로는 이 알람의 서항 해당 여부와 동일 기준시각 연결을
  확인할 수 없다.
- 실증 결과는 센서와 CCTV의 공간 결합, 지역 특화 모형, 예측 대 실측 검증을 후속 과제로 남긴다
  (p.60-62).

### 3.2 자사 기획자료의 역할

`지능형재난안전솔루션(쿠비아)_요약설명자료_v0.2_20260908.pptx` 슬라이드 2는 사전 감시부터 감지,
종합 판단, 영향 예측, 전파·조치, 현장 보고, 자동 기록, 학습·대비까지 8단계 제품 흐름을 제시한다.
`창원시_지능형재난안전솔루션(쿠비아)_REV 1.0.pdf` p.19는 대응 이력 기반 모의훈련 시나리오와 분기·실행 이력 관리를
제품 방향으로 제시한다. 이는 대표 사건 이후의 학습·대비 범위 근거이며 D0~D8에 훈련 편집 기능을
추가한다는 뜻은 아니다.

이는 대표 데모의 설명 구조에는 사용할 수 있지만, 서항 데이터가 확보됐거나 각 단계가 현재 자동
수행된다는 근거는 아니다. `원클릭 시설물 제어`, `1~8단계 자동 수행`과 경쟁사 대비 문구도 Phase 2의
확정 기능으로 그대로 사용하지 않는다.

같은 자료 슬라이드 3의 경쟁사 기능 비교표는 **시연에서 무엇을 강조할지 고르는 근거**로 쓴다. 대외적으로
보유·실증 기능을 설명하는 근거로는 쓰지 않는다(README §4.1). 비교표에서 CUVIA만 `◎`인 항목은 VLM·생성형 AI, 복합 위험도 분석, 자동 보고서·기록,
모의훈련 넷이고, CUVIA가 `X`인 항목은 CAP 표준 경보다. 대표 데모는 이 넷을 각각 한 장면에서 드러내고,
CAP는 이미 채택한 표준이므로 전파문 구조로 흡수한다(§11).

### 3.3 현재 원본 대조 결론

- **대표 유형:** 창원 도시침수는 관측·예측·시설·모형·실증 근거가 있어 유지한다.
- **적용 지역:** 서항은 현장 CCTV와 배수펌프장 위치 근거가 있으므로 우선 후보로 유지한다.
- **미확인 연결:** 서항 배수권역 경계, 그 안의 도로·관로수위계, 펌프 운영값과 도시침수예측판의 연결은
  현재 원본만으로 확인되지 않는다.
- **과거 시각 후보:** 2024년 9월 20일 창원 실증은 재생 시나리오 후보지만 원본 로그를 확보하기 전에는
  서항의 실제 사건으로 사용하지 않는다.

현재 확보한 원본만으로 통과한 P0 항목은 없다. 따라서 사건명은 `창원 검증 배수권역 복합침수 위험`,
서항은 `적용 후보` 상태를 유지한다.

### 3.4 추가 확인이 필요한 것

- 서항의 정확한 배수구역 경계와 관로·도로수위계 매핑
- 제2배수펌프장의 실시간 상태와 가동 대수 데이터 제공 여부
- 서항 대상 실시간 도시침수예측 결과의 공간·시간 해상도
- CCTV 실영상 사용 권한과 VLM 분석 가능 여부
- 기상청 특보 API 인증과 국립해양조사원 신규 조위 대체 API의 과거 조회·기준면
- 생활안전지도 WMS의 외부 데모·배포 사용조건과 필수 출처 표기
- 도로·건물·인구·재난약자 영향 산출에 사용할 최신 기준 데이터
- 공식 임계치, 담당 부서, SOP, 전파 대상과 승인 절차

확인 전까지 위치·수치·결과는 수집·시연 방식 `모의`로 표시한다. `연계 가정`은 상태축 값이 아니라
어떤 연계를 가정했는지 설명하는 근거 주석으로만 사용한다.

## 4. 사건 정의

| 항목 | 기준안 |
|---|---|
| 사건명 | 창원 검증 배수권역 복합침수 위험 |
| 적용 후보 | 서항 - 실제 배수권역·장비 매핑 확인 전 가칭 |
| 사건 유형 | 도시침수 - 내수 중심 복합침수 |
| 원인 조건 | 집중호우 또는 예측강우 상승 |
| 악화 조건 | 높은 조위, 관로 여유 저하, 배수펌프 가용성 저하, 확보된 경우 저류 여유 저하 |
| 직접 징후 | 관로수위 급상승, 도로수위 상승, CCTV 물고임 |
| 영향 대상 | 저지대 도로, 건물, 교통, 보행자, 취약대상 |
| 공간 범위 | 확인된 적용 배수권역과 실제·예상 침수 폴리곤 |
| 운영 목표 | 침수 발생 전 감시 강화, 영향 예측, 통제·전파·배수 대응 결정 |

이 사건은 `호우특보`, `관로수위 경보`, `VLM 침수 감지` 중 하나와 동일하지 않다. 서로 다른 이벤트가
연결되어 만들어진 담당자의 업무 단위다.

펌프 가용성 저하는 우선 복합침수 사건의 악화 조건으로 연결한다. 펌프 고장이 별도 담당 조직·조치·상태를
가져야 할 때만 기반시설 장애 사건으로 분리하고 복합침수 사건과 `악화` 또는 `파생` 관계를 맺는다.

| E10 | 데이터 지연·결측·복구 판정 | 파생 | `DATA_QUALITY_CHANGED` | CUVIA 품질 규칙 | 내부 생성 | 근거 품질과 미확인 구간 |

E7은 같은 사건 시각의 사용 승인 영상이 재생 묶음에 있을 때 원본 재생으로 사용한다. 없으면 재생안에서는
제외하거나 `영상 미확보`로 표시하고, 혼합·완전 모의안에서는 승인 표본 또는 합성 영상·분석임을 명시한다.
다른 지역·시점의 승인 영상을 대표 사건 맥락에 맞게 사용하면 `승인 표본` 출처와 원 촬영시각을 밝히며,
그 영상에서 사건별 VLM 문장을 새로 구성한 부분은 `합성 데이터·모의`로 구분한다. 사용 승인은 시연 방식이
아니라 데이터 사용권한이다.

각 실제 이벤트 인스턴스는 데이터 출처, 연계 준비도, 시연 방식, 데이터 품질과 계산 주체를 기록한다.
`연계 가능`은 현재 API가 연결됐다는 뜻이 아니라 원본에서 연계 대상이나 경로가 확인됐다는 뜻이다.

데이터가 없으면 같은 이벤트 계약의 합성 데이터로 보완한다.

| 이벤트 | 우선 구성 | 현재 판정 | 미확보 시 대체 | 상태 칩 값 |
|---|---|---|---|---|

합성 데이터끼리는 독립적으로 숫자를 정하지 않는다. E0~E6의 시간차·임계치·시설 가용성과 E8의 화면
변화가 하나의 인과 시나리오로 설명돼야 하며, 실제 기관 기준이나 모델 성능을 모사했다고 주장하지 않는다.

### 5.5 합성 데이터의 인과·시간 정렬 규칙

혼합 데모는 실제 API 값 사이의 빈칸에 임의 숫자를 끼우는 방식으로 만들지 않는다. 먼저 하나의
`scenarioBaseTime`과 사건 서사를 정하고, 아래 상대 순서에 맞춰 합성 이벤트를 작성한다. 상대 시각은
시나리오 편집값이며 실제 물리 지연이나 운영 임계치가 아니다.

```text
예측강우·특보·조위 맥락
→ 강우 관측 증가
→ 관로수위 상승과 변화율 이벤트
→ 펌프·저류 여유 등 배수 제약 확인
→ 도로수위 상승과 기준 진입
→ 영상·현장 교차확인
→ 사건 확정
→ 기준 전망·합성 예측면
→ 담당자 승인·조치
→ 수위 하강·현장 결과·종료 검증
```

- E1처럼 실제 API를 사용하는 이벤트는 원래 기준·관측시각과 값을 보존하고, 합성 E0·E2~E7은 그
  기준시각에 맞춘 시나리오 시각을 별도로 가진다. 다른 날짜·지역의 값을 실제 동시 관측처럼 합치지 않는다.
- E4b·E5b·E10은 대응하는 원천 또는 합성 입력을 `derivedFrom[]`으로 참조하고 규칙 ID·버전을 남긴다.
- E6 시설 상태는 사건 전부터 존재한 악화 조건인지, 침수 뒤 발생한 파생 장애인지 시간 순서와 관계를
  분명히 한다. 대표 사건에서는 우선 악화 조건으로 사용한다.
- E8 합성 예측면은 E0~E6과 방향상 일치해야 하지만 침수심·도달시간·대안 효과의 정확도를 주장하지
  않는다. 실제 계산 결과가 확보되면 모델·버전·입력·기준시각과 함께 교체한다.
- D0에서는 사건을 만들지 않고, D1의 복합 징후에서 후보를 만든다. D2의 담당자 확인 전에는
  `확인됨`으로 바꾸지 않는다. E9 현장 결과와 Outcome은 조치 이후 D8에서 기록한다.
- 모든 합성 이벤트에 `scenarioRuleId`, `scenarioRuleVersion`, `generatedAt`, `scenarioTime`,
  `dataOrigin`, `ingestionMode`, `sourceReadiness`, `quality`, `calculationActor`를 남긴다.

## 6. 시연 전제와 정직한 표시

| 상태축 | 데모 표시 |
|---|---|
| 연계 준비도 | `실연계`, `연계 가능`, `협의 필요`, `내부 생성` |
| 수집·시연 방식 | `실시간`, `재생`, `모의`, `수동` |
| 데이터 품질 | `정상`, `지연`, `결측`, `의심`, `보정`과 관측시각 |
| 계산 주체 | `CUVIA 계산`, `외부 모델 수신`, `해당 없음`, 모델명·버전·기준시각·입력·가정 |

원본에서 연계 항목이나 경로만 확인된 경우는 `사업 원본 확인`을 근거 배지로 추가할 수 있지만, 이를
`실연계` 상태 대신 사용하지 않는다.

사건 전체에는 `scenarioMode=정렬된 과거 재생`, `scenarioMode=혼합 데모` 또는
`scenarioMode=완전 모의` 중 하나를 둔다. 혼합 데모에서는 확보 가능한 실제 API·원본 재생·승인 표본과
미확보 내부 연계를 대신하는 합성 데이터를 함께 쓸 수 있다. 모든 이벤트는 하나의 사건 기준시각에 맞추고
`dataOrigin=실제 API|원본 파일|승인 표본|합성 데이터|사용자 입력`과 `ingestionMode`를 함께 표시한다.
담당자의 결정·현장 입력은 어느 시나리오에서도 `수동`일 수 있다.

이 네 운영 투명성 축은 D0~D8의 사건 공통 헤더에서 계속 확인할 수 있어야 한다. D4~D5에서는 모델·버전과
계산 주체를 더 강조한다.

## 7. 대표 시연 흐름

### D0. 사전 감시 - 어디를 먼저 봐야 하는가

**상황**

- 예측강우가 상향되고 만조 시간과 겹친다.
- 공식 호우특보가 발표되거나 단계가 변경되어 감시 강화의 공식 맥락이 생긴다.
- 시스템은 침수흔적·배수취약성·예측강우를 결합해 적용 후보 지역을 감시 우선구역으로 제안한다.
- 인근 CCTV와 핵심 센서를 우선 감시 대상으로 묶는다.

**보여줄 것**

- 창원 전체 위험 개요
- 감시 우선순위와 선정 근거
- 예측의 기준시각과 유효시간
- 데이터 지연·결측 상태

**핵심 메시지**

> 아직 침수 사건이 확정된 것은 아니지만, 어디를 먼저 확인해야 하는지 미리 좁힌다.

### D1. 이상 징후 - 무엇이 변했는가

**상황**

- 관로수위가 빠르게 상승하고 도로수위도 뒤따라 움직인다.
- 반복 알람은 하나의 변화 흐름으로 정리된다.
- 시스템이 `창원 검증 배수권역 복합침수 위험` 사건을 `후보` 상태로 생성한다.

**보여줄 것**

- 원천 관측과 정규화 이벤트
- 임계치뿐 아니라 변화율과 시간차
- 원천 시각과 수신 시각
- 사건 후보에 연결된 이유

### D2. 교차확인 - 정말 같은 사건인가

**상황**

- 조위가 높아 자연배수가 불리하고 펌프·저류시설 가용성 정보가 추가된다.
- 일부 도로수위가 정한 기준에 진입해 관로 상승이 지표면 영향으로 이어지는지 확인한다.
- VLM이 CCTV에서 차로 물고임을 추정한다.
- 담당자가 실제 영상을 열어 분석 결과를 확인한다.

**보여줄 것**

- 강우·관로·도로·조위·시설·영상 근거의 시간 정렬
- VLM 설명, 신뢰도, 모델·버전과 분석 시각을 실제 영상과 나란히
- 담당자의 `확인`, `오탐`, `추가 확인` 선택
- 중복 후보가 있으면 병합하고, 원인·담당 조직·조치·처리상태가 독립적으로 움직이면 별도 사건으로
  분리해 관계를 기록하는 예외 경로
- 의심·지연 데이터 경고

**상태 전환**

`사건 후보 → 담당자가 검토 인수 → 확인중 → 영상·현장·기관 근거 확인 → 확인됨`

### D3. 현재 판단 - 왜 위험한가

**상황**

- 시스템은 공식 특보의 단계·유효시간을 상황 맥락으로 두되, 이를 사건 위험도와 동일시하지 않는다.
- 심각도·긴급도·확실성·추세를 독립적으로 판단하고 위험 요인, 완화 요인, 반대 근거,
  불확실성과 누락 데이터를 함께 제시한다.

**보여줄 것**

- 공식 특보: 단계, 발표·갱신시각, 유효시간과 대상지역
- 위험판단 4요소: 심각도, 긴급도, 확실성, 추세
- 위험 요인: 강우 지속, 관로 상승, 높은 조위, 펌프 가용성 저하, 확보된 경우 저류 여유 저하
- 완화 요인: 아직 낮은 도로수위, 정상인 일부 시설, 확보된 경우 남은 저류 여유
- 반대 근거: 위험 판단과 일치하지 않는 관측·영상·시설 상태
- 불확실성: 센서·영상·예측의 품질과 일치 정도
- 다음 확인이 필요한 데이터

### D4. 기준 전망 - 그대로 두면 어떻게 되는가

**상황**

- 같은 사건에 정렬된 외부 예측판을 불러오거나, CUVIA 실행 범위가 확인된 경우 현재 강우와 배수 조건이
  유지되는 기준 시나리오를 실행한다.
- 디지털트윈은 시간대별 침수 범위와 도달시간을 보여준다.

**보여줄 것**

- 현재 상태와 미래 예측의 명확한 분리
- 확보된 결과의 유효시점별 예측(예: 10·30·60분)
- 도로·건물·중요시설의 예상 영향
- 모델 입력, 기준시각과 불확실성

### D5. 대안 비교 - 무엇을 바꾸면 달라지는가

대안은 실제 원격제어를 가장하지 않는다. 담당자가 선택한 운영 가정을 비교한다.

| 시나리오 | 조건 | 비교 목적 |
|---|---|---|
| A 기준 전망 | 현재 강우·조위·펌프 가용성 유지 | 조치하지 않을 때 영향 |
| B 배수 대응 | 펌프 가용성 회복 또는 확보된 저류·추가 배수 가정 | 침수심·지속시간 변화 |
| C 통제 대응 | 침수 자체는 같고 취약도로를 선제 통제 | 인명·교통 노출 감소 |

시설 조작이 분석 범위를 벗어나면 B를 제외하고 `기준 전망 + 통제 대응`만 비교한다. 필요한 입력이나
영향 계산 기능이 없어 대안을 계산할 수 없으면 `대안 계산 불가`와 필요한 데이터를 표시한다.

제품 범위상 지원하지 않거나 실행을 요청하지 않은 대안은 `계산 미지원·미실행`으로 표시한다. 실제로
실행을 시작한 모델이 오류로 끝난 경우에만 `계산 실패`와 `MODEL_RUN_FAILED`를 기록하고 실패 원인과
대체 경로를 남긴다. 재생안은 과거에 생성된 예측판을 보여주는 것이므로 현재 모델을 실행한 것처럼
표현하거나 실행 실패 이벤트를 새로 만들지 않는다.

### D6. 영향 기반 대응 - 무엇을 결정할 것인가

**상황**

- 예측 결과의 도로, 건물, 대상자와 도달시간이 SOP 초안에 연결된다.
- 시스템이 권고와 전파문을 만들고 담당자가 수정·승인한다.
- 대응안 승인 뒤 도로 통제, 시설 점검·운영 요청 또는 전파 중 하나 이상의 첫 조치가 시작된다.

**보여줄 것**

- 권고 이유와 반대 근거
- 통제 대상 도로와 담당기관
- 전파 대상 지역·수신자·매체
- 전파문의 CAP 1.2 필드 구성: 식별자, 심각도·긴급도·확실성, 대상지역, 갱신·취소
- 시설 점검·운영 요청
- 승인자와 승인시각

**상태 전환**

`확인됨 → 대응안 승인·첫 조치 시작 → 대응중`

### D7. 실행 결과 - 실제로 되었는가

**상황**

- 알림톡·마을방송·전광판·기관 통보와 시설 요청의 결과가 채널별로 들어온다.
- 한 채널은 실패하도록 구성하고 대체조치를 기록한다.
- 위험의 급격한 확대가 멈추고 조치가 유지되는 감시 단계에 들어가면 담당자가 사건을 `통제`로 전환한다.

**보여줄 것**

- 성공·실패·미응답·확인대기
- 실패 이유와 재시도
- 유선 연락·대체 매체 등 대체조치
- 현장 담당자의 도로 통제·시설 점검 결과

**상태 전환**

`대응중 → 위험 확대 중단·잔여 조치 감시 → 통제`

### D8. 종료와 검증 - 예측과 대응은 어땠는가

**상황**

- 강우가 약해지고 관로·도로수위가 하강한다.
- 담당자가 종료 조건을 확인한다.
- 사건 타임라인과 상황보고서 초안을 생성한다.

**보여줄 것**

- 실제 비교 자료가 있으면 예측 침수심·도달시간 대 실제 관측
- 비교 자료가 있으면 과대·과소예측, 없으면 검증 대기 사유와 필요한 관측
- 최초 감지·후보 생성·확인·전파·조치·통제·종료 시간
- 성공·실패·대체조치
- 다음 임계치·모형·SOP 검토 항목
- 상황보고서 항목에서 원천 이벤트·결정·실행 기록으로 이동하는 근거 링크
- 이 사건의 대응 이력으로 `대응 모의훈련` 시나리오 후보를 만드는 진입점. 훈련 편집·실행은 데모 밖

**상태 전환**

`통제 → 종료 조건 확인·잔여사항 기록 → 종료`

## 8. 디지털트윈 화면의 역할

대표 데모에서 디지털트윈은 다음 다섯 영역을 가져야 한다.

| 영역 | 답하는 질문 | 대표 내용 |
|---|---|---|
| 현재 상태 | 지금 실제로 무엇이 관측됐는가? | 강우·관로·도로·조위·펌프·저류시설·CCTV |
| 기준 전망 | 현재 조건이 유지되면 어떻게 되는가? | 시간대별 침수심·범위·도달시간 |
| 대안 전망 | 무엇을 바꾸었고 무엇이 달라지는가? | 배수 가용성·통제 시점과 기준 대비 차이 |
| 영향 결과 | 누가·어디가·언제 영향을 받는가? | 도로·건물·중요시설·대상자 |
| 근거·한계 | 무엇으로 계산했고 얼마나 믿을 수 있는가? | 모델·버전·입력·품질·불확실성 |

3D 침수면은 영향 결과를 이해하기 위한 표현 중 하나다. 슬라이더로 임의 수위를 올리는 장면만으로
예측이라고 부르지 않는다.

## 9. 시스템과 담당자의 역할

| 시스템 | 담당자 |
|---|---|
| 이벤트 수집·정규화·중복 제거 | 결측·이상·현장 맥락 확인 |
| 사건 후보와 연결 이유 제안 | 사건 확인·병합·분리·오탐 판단 |
| VLM 장면 설명과 신뢰도 표시 | 실제 영상 확인 |
| 기준·대안 예측과 영향 계산 | 사용할 조건과 대응안 선택 |
| SOP·전파문·보고서 초안 | 수정·승인·실행·최종 확정 |

`담당자`는 검토 담당자와 승인자를 포함하는 역할군이다. 실제 기관에서 두 역할이 분리되면 결정마다
제안자·검토자·승인자와 시각을 각각 기록한다.

“1~8단계를 자동 수행한다”보다 **반복 수집·정리는 자동화하고 판단 근거와 승인 경계는 명확히 한다**고
설명한다.

## 10. 화면 동선 원칙

최종 화면 번호와 메뉴는 IA 단계에서 정한다. 이 문서에서는 업무 질문만 고정한다.

```text
도시 전체 감시
→ 사건 후보와 근거 확인
→ 현재 위험 판단
→ 디지털트윈 기준·대안 비교
→ 대응 승인과 실행
→ 결과·예측 검증과 보고서
```

- 시연자는 메뉴를 순서대로 누르지 않고 사건 안의 다음 행동으로 이동한다.
- 화면이 바뀌어도 `incidentId`, 기준시각, `workflowStatus`, `selectedForecastId`,
  `affectedGeometryId`, `selectedEvidenceId`, `pendingDecisionId`, `scenarioMode`와 이벤트별
  `dataOrigin`·`ingestionMode`가 유지된다.
- AI 검색은 독립된 결론 화면이 아니라 현재 사건의 근거를 찾고 해당 화면으로 이동시키는 보조 기능으로
  우선 검토한다.

## 11. 시연 완료 기준

### 핵심 완료 기준

- 서로 다른 출처의 관측·예측·시설·현장 근거가 하나의 사건에 연결된다.
- 왜 같은 사건에 연결됐는지 시간·공간·의미 근거가 보인다.
- 원천 이벤트와 사건 상태가 구분된다.
- 현재 상태와 기준 전망이 구분된다.
- 사건의 영향 근거가 대응 대상·전파·조치 기록으로 이어진다.
- 실행 실패와 대체조치가 기록된다.
- 후보 생성부터 확인·승인·실행·통제·종료까지 이벤트와 상태 변경의 감사 추적이 남는다.
- 모든 `dataOrigin`, 연계 준비도, 시연 방식, 데이터 품질과 계산 주체가 구분된다.

### 시연에서 드러낼 차별점

§3.2의 비교표에서 고른 항목이 어느 장면에서 보이는지 고정한다. 새 화면을 만들지 않고 해당 단계의
카드·문안 구성으로 해결한다.

| 비교표 항목 | 비교표 표기 | 장면 | 드러내는 방법 | Phase 1 자산과 부담 |
|---|---|---|---|---|
| VLM·생성형 AI | CUVIA만 `◎` | D2, 공통 AI 보조 | VLM 문장·신뢰도·모델·버전을 실제 영상과 나란히 | CCTV 독·영상 영역과 VLM 문장 있음. 모델·버전 필드 추가. 낮음 |
| 복합 위험도 분석 | CUVIA만 `◎` | D3 | 심각도·긴급도·확실성·추세 4축과 반대 근거·불확실성 | 위험도 카드 있음. 4축 분리와 반대 근거 칸 추가. 낮음 |
| 자동 보고서·기록 | CUVIA만 `◎` | D8 | 타임라인에서 생성한 보고서와 항목별 근거 링크 | 보고서 페이지와 사건 타임라인 있음. 항목→이벤트 링크 연결. 중간 |
| 모의훈련 | CUVIA만 `◎` | D8 | 대응 이력에서 훈련 시나리오 후보를 만드는 진입점 하나 | 없음. 카드 한 장이라 낮음. 편집·실행은 만들지 않음 |
| CAP 표준 경보 | CUVIA `X` | D0 특보, D6 전파문 | 특보 헤더와 전파문을 CAP 1.2 필드로 구성. 실제 발령은 하지 않음 | 전파 팝업 있음. 문안 카드를 필드 구조로 재배치. 낮음 |
| 예측·시뮬레이션, 트윈 | `△` | D4~D5 | 기준·대안 예측판 비교와 근거·한계·불확실성 구간 공개 | 트윈 페이지·시간축·영향·근거 카드 있음. 기준/대안 두 판 비교와 구간 표시 추가. 중간 |
| 예경보 매체 제어 | `△` | D6~D7 | 요청·승인·결과 확인과 실패·대체조치 기록 | 실행 팝업과 결과 표시 있음. 실패→대체조치 연결 추가. 낮음 |

부담은 기획·디자인 작업 기준이다. 낮음은 기존 화면의 카드·필드 구성 변경, 중간은 두 화면 사이의
연결이나 새 비교 뷰가 필요한 경우다. 높음에 해당하는 항목은 없으며, 모두 Phase 1 자산 위에서
해결한다.

### 데이터 확보 시 강화 기준

- 영상 사용이 가능하면 VLM 결과와 담당자 확인을 구분한다.
- 같은 사건·기준시각에 정렬된 대안 예측판을 받을 수 있으면 기준 전망과 대안 전망을 비교한다.
- 대안 결과가 없으면 현재 상태와 기준 전망을 중심으로 설명하고 대안의 조건 구조와 `계산 미지원·미실행`
  상태만 보여준다. 이 경우 대안 적용 효과를 주장하지 않는다.
- 영향 기준 데이터를 확보하면 예측 영향을 실제 SOP 대상과 전파문에 연결한다.
- 실제 관측·현장 결과가 있으면 예측 침수심·도달시간과 비교한다.

P0는 대표 사건과 시연 방식 자체를 결정하는 필수 확인 항목이다. P1은 시연의 구체성과 신뢰도를
높이는 항목이며, P2는 검증 메시지를 강화하는 항목이다. 확인되지 않은 값을 실제 사실처럼 임의 보완하지
않으며, 합성 데이터가 필요하면 오른쪽 열의 구성 원칙과 출처 표시를 적용한다.

현재 원본 검토 결과 P0 네 항목은 모두 `부분 확인`이다. 다음 검토에서는 자료가 있다는 설명이 아니라
실제 파일·API 명세·식별자·기준시각을 받아 각 항목을 `확인` 또는 `미확보`로 닫아야 한다.

P0 확인 결과에 따라 사건의 현상·예측 데이터는 다음 세 방식 중 하나를 선택한다.

1. **정렬된 과거 재생:** 같은 과거 사건·기준시각에 속하는 E0~E8만 함께 재생한다. 시설·영상·대안
   예측판이 그 묶음에 없으면 모의로 보충하지 않고 `미확보` 또는 `계산 미지원·미실행`으로 표시한다.
2. **혼합 데모:** 실제 API·원본 파일·승인 표본·합성 데이터를 하나의 사건 기준시각에 맞춰 조합한다.
   이벤트마다 `dataOrigin`과 `ingestionMode`를 표시하고, 다른 지역·시점의 자료를 사건에 맞게 바꾼 경우
   원본 재생이 아닌 합성 데이터로 분류한다.
3. **완전 모의:** 정렬된 과거 묶음이 없으면 E0~E8 전체를 하나의 모의 사건 세트로 만들고 화면 전체에
   `모의`를 표시한다. 기준·대안 예측면을 포함할 수 있지만 이는 화면·업무 흐름을 설명하는 예시이며
   실제 모델 성능이나 대안 효과로 주장하지 않는다.

담당자의 결정·현장 입력은 세 방식 모두 시연 방식 `수동`, 시연 중 CUVIA가 실제 생성한 업무 이벤트는
`실시간`으로 남기며 연계 준비도는 모두 `내부 생성`이다. 이는 현상·예측 데이터 혼합이 아니다. 과거
자료와 합성 데이터를 조합할 때도 사건 기준시각과 출처 표시를 유지한다.

정렬된 원본·재생 자료와 실제 모델 결과로 전체 흐름을 구성할 수 있을 때 A 유형을 R2 시연으로 올린다.
혼합 데모나 완전 모의만 가능한 동안에는 R1 설계를 유지한다. 합성 결과 화면에 별도 면책 배지를 두지 않고,
사건 헤더의 데이터 상태 칩과 시연 대본·문서가 합성 결과임을 든다.

모든 축소안을 적용해도 이벤트를 사건으로 묶는 이유, 근거와 한계, 담당자 승인, 실행·결과 기록은 데모로
증명할 수 있다. 다만 실제 기준·대안 결과가 없으면 디지털트윈의 비교 효과는 제품 방향 가설로만 보여주며
보유 모델의 성능이나 실제 대응 효과로 설명하지 않는다.

확인 결과에 따라 세부 값과 화면 표현은 바꿀 수 있지만, `수집→사건화→교차확인→기준 전망→
영향 기반 대응→결과 기록`이라는 골격은 유지한다. 대안 예측과 실제 대비 성능 검증은 해당 데이터를
확보했을 때 이 골격에 추가한다.
