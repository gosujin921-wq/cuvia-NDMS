Phase 2가 답해야 할 다섯 질문

  1. CUVIA는 어떤 원천 데이터와 이벤트를 수집하는가?
  2. 서로 다른 이벤트를 어떤 기준으로 하나의 재난 사건에 연결하는가?
  3. 사건 유형에 따라 디지털트윈의 입력, 시간축, 공간 표현과 결과가 어떻게 달라지는가?
  4. 예측 결과가 담당자의 판단, SOP, 전파, 조치와 기록으로 어떻게 이어지는가?
  5. 이 방향을 한 건의 대표 사건으로 어떻게 이해하기 쉽게 시연할 것인가?
설계 원칙 (README §5)
  • 사건 중심: 센서나 기능 목록보다 담당자가 판단하고 대응할 사건이 중심이다.
  • 원천과 판단 분리: 수집값, 관측 이벤트, 시스템 판단, 담당자 확인을 구분한다.
  • 현재와 미래 분리: 현재 관측, 조건 유지 전망, 대안 전망과 실제 결과를 구분한다.
  • 공통 골격과 유형별 차이: 업무 흐름은 공통으로 두고 트윈의 입력·표현·결과는 유형별로 설계한다.
  • 사람 승인: AI와 예측은 근거와 권고를 제공하며 되돌리기 어려운 조치는 담당자가 확정한다.
  • 근거 추적: 화면의 판단과 예측 결과는 사용한 데이터, 시각, 출처와 가정으로 돌아갈 수 있어야 한다.
  • 정직한 상태 표시: 연계 준비도, 수집·시연 방식, 데이터 품질, 계산 주체와 트윈 표현 준비도를 서로 다른 축으로 구분한다.
  • 대표 데모 집중: 모든 유형의 전체 흐름을 구현하지 않고 한 사건으로 깊이를 증명한다.
  • 수량 비목표: 화면, 사건, 재난유형 수를 Phase 2의 성과로 삼지 않는다.

먼저 가르는 세 축

기존 문서와 화면에서 이벤트 유형, 재난유형, 처리상태가 섞이면 같은 단어가 서로 다른 질문에 답하게 된다. Phase 2에서는 아래 세 축을 독립적으로 관리한다.

축답하는 질문예시
이벤트 유형무엇이 발생하거나 변했는가?수위 관측, 특보 발표, 펌프 상태 변경, 현장 보고
재난유형어떤 위험과 사건에 관련되는가?내수침수, 하천범람, 태풍, 산불, 폭염

하나의 수위 관측 이벤트는 내수침수·하천범람·폭풍해일 사건에 각각 근거가 될 수 있다. 반대로 하나의 내수침수 사건에는 강우, 관로수위, 도로수위, 펌프 상태, 조위, CCTV와 현장 보고가 함께 연결될 수 있다.

도시 대응단계는 개별 Incident의 workflowStatus가 아니라 별도 CityOperationalState로 관리한다. 변경 시 CITY_STAGE_CHANGED 업무 이벤트를 남기고, 변경을 승인한 Decision과 해당 시점의 관련 사건을 연결한다. Incident에는 판단 당시 도시 대응단계의 참조만 보존한다.

  • pendingDecisionId는 decisions[] 중 검토중 상태인 결정안을 가리킨다.
  • 조치 결과 상태는 대기·진행중·성공·실패·미응답·확인대기·대체됨·취소로 통일한다.
  • ACTION_*은 현장 확인·도로 통제·시설 점검과 운영 요청처럼 사람이 수행하는 업무에 사용한다.
  • CONTROL_*은 장비에 실제 원격제어 명령을 보내는 경우에만 사용하며 Phase 2 대표 데모에서는 쓰지 않는다.
  • DISSEMINATION_*은 알림톡·방송·전광판·기관 통보 등 메시지 전파 요청과 채널별 결과에 사용한다.

사건 후보가 만들어지는 조건 (01 §7.1)

사전 감시는 아직 Incident가 아니다. 예측강우·특보·취약성만으로는 감시 우선구역·카메라·시설을 선정하고, 위험이 해소되면 별도 사건 상태 전환 없이 감시 우선순위에서 내린다.

다음 중 하나가 발생하면 Incident를 후보 상태로 만들 수 있다.

  • 공식 특보·기관 사건이 새로 발표됨
  • 핵심 센서가 심각 임계치를 통과함
  • 여러 센서의 변화가 동일 구역과 시간창에서 함께 나타남
  • VLM 또는 현장 보고가 명시적인 위험 장면을 확인함
  • 예측 결과가 사전에 정한 사건 후보 영향 기준을 초과함
  • 담당자가 수동으로 사건을 등록함

예측 갱신 자체는 후보 생성 조건이 아니다. 대표 데모에서는 예측강우 상향으로 D0 감시 우선대상을 정하고, 관로수위 급상승과 복합 징후가 발생하는 D1에서 사건 후보를 만든다. 후보 생성은 사건 확정이 아니다.

대표 데모는 화면 수나 재난유형 수를 보여주는 영상이 아니다. 한 사건을 통해 다음 질문에 답해야 한다.

CUVIA가 서로 다른 이벤트를 왜 하나의 사건으로 묶었고, 앞으로의 영향을 어떻게 비교했으며, 담당자가 어떤 근거로 대응을 결정했는가?

데모가 끝났을 때 다음 다섯 가지가 기억되어야 한다.

  1. 여러 시스템의 이벤트가 하나의 사건 근거로 연결된다.
  2. AI와 예측의 결론만이 아니라 사용한 데이터와 가정이 보인다.
  3. 디지털트윈은 3D 효과가 아니라 현재 조건과 대안을 비교하는 판단 도구다.
  4. 시스템 권고와 담당자 확인·승인이 분리된다.
  5. 실행 성공·실패와 실제 결과가 사건 기록으로 남는다.

P0는 대표 사건과 시연 방식 자체를 결정하는 필수 확인 항목이다. P1은 시연의 구체성과 신뢰도를 높이는 항목이며, P2는 검증 메시지를 강화하는 항목이다. 확인되지 않은 항목을 임의 수치로 메우지 않고 오른쪽 열의 축소안을 적용한다.

현재 원본 검토 결과 P0 세 항목은 모두 부분 확인이다. 다음 검토에서는 자료가 있다는 설명이 아니라 실제 파일·API 명세·식별자·기준시각을 받아 각 항목을 확인 또는 미확보로 닫아야 한다.

P0 확인 뒤 시연 데이터는 다음 두 방식 중 하나만 선택한다.

  1. 정렬된 과거 재생: 같은 과거 사건·기준시각에 속하는 관측, 시설, 영상과 기준 예측판을 함께 재생한다. 대안 예측판이 없으면 대안의 조건과 미지원 상태만 보여주고 결과 차이를 주장하지 않는다.
  2. 완전 모의: 정렬된 과거 묶음이 없으면 관측, 시설, 영상, 기준·대안 예측을 하나의 모의 사건 세트로 만들고 화면 전체에 데모 모의를 표시한다.

과거 관측을 재생하면서 그 사건과 정렬되지 않은 모의 예측을 결합하지 않는다.

확인 결과에 따라 세부 값과 화면 표현은 바꿀 수 있지만, 수집→사건화→교차확인→기준 전망→ 영향 기반 대응→결과 기록이라는 골격은 유지한다. 대안 예측과 실제 대비 성능 검증은 해당 데이터를 확보했을 때 이 골격에 추가한다.

현재 사건과 화면의 근거를 요약하고 사용자를 해당 정보로 이동시킨다. 별도의 판단 결과를 만드는 독립 사일로로 두지 않는다.

허용 역할

  • 현재 사건 요약과 누락 정보 안내
  • 특정 판단에 사용된 관측·예측·SOP 근거 찾기
  • 유사 사건·과거 결정 탐색
  • 전파문·상황보고서 초안 작성
  • 답변 근거가 있는 화면·이벤트·문서로 이동

제한

  • 원천에 없는 사실 생성 금지
  • 확실성·한계를 숨긴 단정 금지
  • 담당자 승인 대행 금지
  • 근거 링크 없는 위험도·대응 결론 금지

CUVIA의 디지털트윈은 3D 지도를 뜻하지 않는다.

사건 시점의 관측 상태와 기준 데이터를 공간에 정렬하고, 조건을 유지하거나 바꿨을 때의 미래 상태와 영향을 비교해 대응 결정을 지원하는 사건별 작업 공간이다.

모든 유형의 트윈은 다음 다섯 질문에 답해야 한다.

  1. 지금 무엇이 관측됐는가?
  2. 현재 조건이 유지되면 언제, 어디까지, 어느 정도 변하는가?
  3. 어떤 조건이나 대응을 바꾸어 비교할 수 있는가?
  4. 사람·시설·도로·지역에 어떤 영향이 예상되는가?
  5. 이 결과는 어떤 데이터·모델·가정으로 만들었고 한계는 무엇인가?

외부 기관이나 협력사 모델이 계산한 결과를 받는 경우에도 CUVIA는 입력 근거, 결과 버전, 사건 연결, 영향 해석과 대응 기록을 관리한다. 자체 계산과 외부 결과 수신을 같은 기능으로 표현하지 않는다.

Phase 2에서 일곱 유형군 모두의 모델과 화면을 구현한다는 뜻이 아니다. A 유형을 대표 데모로 깊게 설계하고 C·D·F는 서로 다른 트윈 문법을 보여주는 비교 기준안으로 둔다. B는 확장 설계, E는 장기 후보로 남기고, G는 다른 사건에서 발생하는 파생 장애로 공통 적용한다. 데이터·모델이 없는 유형은 예상 시나리오를 설명할 뿐 계산이 가능한 기능으로 표현하지 않는다.

Phase 2 역할은 문서와 데모에서 어디까지 다룰지를 뜻하며 R0~R3 준비도가 아니다. 비교 개념은 입력·시간·공간·예상 출력의 구조만 정적으로 설명하고 계산값이나 움직이는 예측면을 만들지 않는 방식이다.

재난명과 유형군

복합재난

복합재난을 한 화면에 모든 레이어를 올리는 방식으로 정의하지 않는다.

상위 조건: 태풍·집중호우
├─ 원인/동시 사건: 하천수위 상승
├─ 주 대응 사건: 창원 검증 배수권역 복합침수
└─ 파생 사건: 도로 단절·펌프 장애·통신 장애
  • 태풍·집중호우는 기본적으로 기상·특보 이벤트와 사건 조건으로 연결한다. 시 전체 대응처럼 독립 담당·조치· 처리상태가 필요할 때만 상위 사건으로 만들며 자동으로 Incident를 생성하지 않는다.
  • 사건마다 주 유형군, 공간 범위, 담당 조직과 상태를 가진다.
  • 동일 이벤트를 여러 사건이 참조할 수 있지만 원천 이벤트를 복제하지 않는다.
  • 원인·동시·파생 관계를 표시하고, 사건을 병합해 책임과 상태를 잃지 않는다.
  • 종합상황에서는 사건 간 영향과 공통 대응만 요약한다.
  • 세부 트윈에서는 해당 사건의 계산·근거·대안에 집중한다.

확정된 원칙

  • Phase 2는 기존 구현의 단순 확장이 아니다.
  • 원본 자료와 추가 조사 결과를 기준으로 새로 설계한다.
  • 이벤트 수집·사건화·활용 구조를 먼저 정의한다.
  • 전체 흐름은 대표 사건 한 건으로 깊게 보여준다.
  • 나머지 유형은 대표 사건과 디지털트윈의 차이를 보여준다.
  • 현재 코드는 Phase 1 현황과 재사용 가능성을 확인하는 자료다.
  • 백업 문서는 복구용이며 새 설계의 근거로 사용하지 않는다.
  • README는 계획을 관리하고 세부 설계는 이벤트·사건, 대표 데모, 유형별 트윈과 IA 문서에서 작성한다.
  • 재난유형은 행정 명칭을 나열하지 않고 계산·시간·공간·판단 방식이 다른 트윈 유형군으로 설계한다.
  • 사건 확인 전 자동화는 내부 수집·정규화·분석·검토 알림으로 제한하고 외부 전파·시설 제어는 담당자가 승인한다.
  • 외부 NDMS 사건은 원본 식별과 변경 이력을 보존하며 CUVIA 사건과 자동 병합하지 않는다.
  • 실제 원격제어는 Phase 2 대표 데모에서 제외하고 시설 요청·승인·결과 확인까지만 표현한다.
  • VLM은 사건 근거와 감시 우선순위를 제공하며 사람의 사건 확정과 대응 승인을 대신하지 않는다.

권고 기준안

  • 대표 데모는 원본 근거가 가장 강한 창원 도시침수를 우선안으로 두고, 서항은 실제 배수권역·센서·시설 매핑을 확인할 우선 적용 후보로 둔다.
  • 비교 유형은 해안 경계·월류, 이동 전선·확산, 지반·구조 영향을 우선 기준안으로 두고 기반시설 장애는 파생 사건으로 공통 적용한다.

권고 기준안은 제품 방향을 구체화하기 위한 우선안이며 확정된 보유 기능이나 구현 범위가 아니다. P0 데이터 확인과 사용자 검토를 통과하면 확정 상태로 전환한다.

아직 결정하지 않은 항목

  • 대표 데모의 실제 서항 배수권역·센서·CCTV·펌프 매핑과 서항 적용 여부
  • Phase 2 비교 기준안 3종의 최종 채택 여부와 각 유형군의 데이터·모델 준비도
  • 사건 후보를 자동 생성·연결할 세부 임계치·시간창·공간 기준
  • 디지털트윈이 직접 계산할 범위와 외부 모델을 받아 표현할 범위
  • 다섯 업무 공간의 최종 화면 구성과 화면 간 전환 방식
